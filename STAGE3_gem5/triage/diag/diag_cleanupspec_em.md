# diag_cleanupspec_em: a squashed RMW upgrades a squashed load's E line to M, and CleanupSpec then skips that load's cleanup (UV3 family, E→M path)

**Issue and signature.** On CleanupSpec (`/work/amulet/amulet-gem5-CleanupSpec_AE-v1.1`, `Cleanup_FOR_L1L2`), with the transmitter emitted as a value-neutral RMW (`orq $0,(mem)`, corpus `testsets_latest/STT_6_rmw`): a squashed load S installs line L in E; the squashed RMW transmitter U (its `ldst` micro-op) hits L and upgrades it, `L1D:hit line=L seq=U req=st … ev=Store st=E nst=M`; after the squash U's cleanup is `cleanup_skip seq=U why=l1hit` (it installed nothing) and S's cleanup is `L1D:cleanup_skip line=L seq=S … ev=Inv_CLEANUP st=M nst=M`. L stays in L1D and L2 (and S's L1D victim, if it had one, is never restored), so `check_footprint` reports `under_clean` on L (L1D + L2) when cold, or on L + S's victim when warm. The diagnostic buckets a stem only if every offending item of every hitting variant is that chain (cause `EM_rmw_squashed` in `cleanupspec_em_evidence.json`, written by `STAGE3_gem5/triage/cleanupspec_em_evidence.py`): S and U never committed, both younger than the squashing branch, U at the record's xmit pc, exactly one E→M hit and exactly one st=M skip. Mixed stems (e.g. a split RMW that is also UV4, not_taken inst-126731), an older committed upgrader (that is CS-1, `diag_cs1_store_upgrade`), or a missing trace stay NEW.

**Example (cold run `results/STT_6_rmw_cleanupspec_footprint_cold__latest`, not_taken inst-021314, kept trace `diagnostics/traces/mispredict_not_taken/inst-021314.pipeview.txt.gz`).** S = seq 3098, `MOV_R_M ld rax, DS:[rax + rsi]` at 0x4042f0 (the access load; it produces U's address register); U = seq 3100, `OR_M_I ldst t1, DS:[rax + rsi]` at 0x4042f4 (the xmit); branch seq 3091 at 0x4042e3 held 5000 cycles.
- `17064500 L1D:fill line=0x75c0 seq=3098 … msg=DATA_EXCLUSIVE … st=NP:nst=IS`, then `ev=Data_Exclusive st=IS:nst=E` (L2 fill id 4392 at 16925500).
- `17066000 L1D:hit line=0x75c0 seq=3100 pc=0x4042f4 req=st msg=ST … ev=Store:st=E:nst=M:lvl=L1`.
- `19417500 ROB:squash seq=3091 sq=4`; `19418000 L1D:cleanup_skip line=0x75c0 seq=3100 … why=l1hit`; `19418000 L1D:cleanup_req line=0x75c0 seq=3098 … mode=exec:lvl=MEM`; `19418500 L1D:cleanup_skip line=0x75c0 seq=3098 … ev=Inv_CLEANUP:st=M:nst=M`.
- No invalidate of 0x75c0 follows; offending items L1D 0x75c0 (event 4450) and L2 0x75c0 (event 4392).

**Root cause (code, `src/` of the AE tree, local copy `~/trippel/defense_src/amulet-CleanupSpec_AE-v1.1/`).**
- The RMW's `ldst` carries `StoreCheck`, so `Sequencer::makeRequest` sends `RMW_Read` with secondary type `ST` (`mem/ruby/system/Sequencer.cc:984-993`); the L1 maps `ST` to `Event:Store` (`MESI_Two_Level-L1cache.sm:329-341`). The mandatory-queue data path triggers it with no speculation check (`:855-905`; only `LD` has the cleanup-inflight drop, `:863-869`).
- `transition({E,M}, Store, M)` (`:2294-2298`) upgrades the line at execute time, for a squashable instruction.
- `transition(M, Inv_CLEANUP)` (`:2701-2705`, action `clirs2_cleanup_L12InvRoll_skip`, `:1737-1749`) then marks S's L1 invalidate, L1 rollback and L2 invalidate as done without doing them. That skip exists for the paper's case "changes made to the cache by older non-squashed loads [and stores] that execute after squashed loads … need to be preserved … corresponding invalidations / restorations are skipped" (CleanupSpec §3.4 p7). M is used as proof that an older non-speculative store owns the line, which holds only if write permission is never requested speculatively, which the paper states as an assumption: "RFOs are issued non-speculatively" (p8 §4). A speculative RMW breaks it.
- Same broken assumption as UV3 (`diag_uv3_rmw`: the squashed RMW's own write-request fill is not undone, `why=nohitinfo`), but a different protocol path: here U hits, the skip is in an older squashed load's cleanup, and the residue is that load's install. AMuLeT's UV3 patch (record hit/miss metadata in `writeCallback`, AMuLeT §4.6 p11) would give U an `L1Hit` and still leave L in M, so by reading it does not fix this path (unverified: no patched build was run).

**Counterfactual (no re-run needed).** The same stems with the original plain-load transmitter (`movq (mem),%r`, a `Load` event; `transition({S,E,M}, {Load, Expose})` at `MESI_Two_Level-L1cache.sm:2257` leaves E as E) do not hit: 72/72 not hit in `results/STT_6_rmwstems_cleanupspec_tbe_l2_3_dc_2_cold__latest` (cold, `L2_TBEs=3`), 72/72 in `results/STT_6_rmwstems_cleanupspec_footprint_random__latest`; and 0 `EM_rmw_squashed` among that control's hits. So the E→M upgrade by the speculative RMW is what disables S's cleanup.

**Is it a leak?** In every case S produces U's address (S < U, 252/252 items), and U hits L only when S's loaded value makes U's address fall in S's line. Whether L survives the squash therefore depends on the speculatively loaded value: the same information UV3 leaks, through S's line instead of U's. Narrow in this corpus (one value class per test), but a value-dependent final cache state that the paper says must not exist.

**Counts (2026-11-09, `cleanupspec_em_evidence.py`, scratch output cafe2 `/tests/simspect_alloy_20261108/bugwork/cleanupspec_em/`).** Cold run: 72 stems (of 82 NEW; the rest 9 UV4 + 1 E→M+UV4 mixed). Random run: 44 (42 cold, 2 warm; of 58 NEW). Warm run `STT_6_rmw_cleanupspec_footprint__20261109_002545`: 10 (the "RMW E→M + victim" set of round 3). Plain-load controls: 0.

**Verdict.** Real CleanupSpec implementation defect (class A: the final cache state depends on a squashed access), same root assumption as AMuLeT UV3 (speculative RFO) but a distinct mechanism and code path that AMuLeT does not list and whose UV3 patch does not cover. Not a checker artifact (S's install is undone in the plain-load control; the skip is a logged protocol transition) and not a harness/timing artifact (in inst-021314 the upgrade is 2.35 M ticks before the squash). Whether to count it as a new bug or as a UV3 variant is Anna's call (URGENT_TODO "CleanupSpec E→M case"). Scope: CleanupSpec footprint campaigns on a memory-RMW transmitter corpus; not deployed to any campaign by the investigating session.
