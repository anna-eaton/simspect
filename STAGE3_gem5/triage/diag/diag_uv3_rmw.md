# diag_uv3_rmw: CleanupSpec skips the undo of a squashed RMW's write-request fill (AMuLeT UV3)

**Issue and signature.** On CleanupSpec (`/work/amulet/amulet-gem5-CleanupSpec_AE-v1.1`, `Cleanup_FOR_L1L2`), a transmitter emitted as a value-neutral RMW (`orq $0,(mem)`, the disjoint corpus `testsets_latest/STT_6_rmw`) executes its `ldst` micro-op under a held mispredict. Ruby turns it into `RMW_Read`/GETX, so the line is installed by a write request (`L1D:fill … req=st:msg=ST`, `L2:fill … req=st:msg=GETX`). After the squash CleanupSpec logs `L1D:cleanup_skip line=<line> seq=<seq> why=nohitinfo` and leaves the line in L1D and L2, so `check_footprint` reports `under_clean`. The diagnostic buckets a hit as UV3 only when, for every hitting variant of the stem, `terms_fired` is exactly `under_clean`, every offending event is such a write-request fill at the xmit pc by an instance that never retired, and the matching `cleanup_skip why=nohitinfo` exists for that line and seq. Everything else (a load-type fill, another pc, a retired actor, no `nohitinfo` skip, a missing trace) stays NEW.

**Evidence and root cause.** Source, per the 2026-11-08 RMW agent (`wiki/design/VOCAB_TABLES.md`, "RMW agent findings (2026-11-08)", CleanupSpec row): `ldst` carries `StoreCheck`, so `Sequencer::makeRequest` issues `RMW_Read` with secondary type `ST` (`Sequencer.cc:984-993`); `Sequencer::writeCallback` (`Sequencer.cc:443-480`) sets only `L1Hit`, never `L2Hit`/`L2Miss`, so the LSQ cleanup path (`lsq_unit_impl.hh:2584-2589`) has no hit info and skips the undo. The A/B demo `uv3rmw` on cafe2 (`/tests/simspect_fixed_20261030/results/STT_6_cleanupspec_v2hooks__20261107/demos/verify/uv3rmw/`) shows the exact line sequence (fill id 65 at tick 163500, `cleanup_skip … why=nohitinfo` id 128 at tick 1164000), while the plain-load control gets `cleanup_inv` at L1D and L2. This is AMuLeT's UV3 ("speculative stores", §4.6 p11, Listing 3/Fig. 7 "WriteCallback() for Spec Store L1Hit: 0, L2Hit: 0, L2Miss: 0"). Evidence per campaign comes from that campaign's own kept traces: run it with `pipeline.keep_tmp: true`, then `python3 STAGE3_gem5/triage/uv3_rmw_evidence.py <campaign>` writes `diagnostics/uv3_rmw_evidence.json` (and gzips the hit traces under `diagnostics/traces/`), which this diagnostic reads.

**Verdict.** Real gem5 defense bug, already known (AMuLeT UV3): the CleanupSpec implementation does not record hit metadata for write-request fills, so it cannot undo them. It is not a checker artifact (the plain-load control is undone) and not a timing artifact (the fill is far before the squash). Scope: CleanupSpec footprint campaigns on the RMW corpus; it matches nothing on a corpus without RMWs. Open and unverified: whether AMuLeT's fix (writeCallback metadata) also covers the speculative GETX invalidating other cores' copies, which CleanupSpec says never happens ("RFOs are issued non-speculatively", p8 §4); a single-core SE run cannot show that.
