PROPOSED, NOT APPLIED (2026-11-08). Concretization for the STT_6_rmwjmp draft model
(STAGE1_alloy/models/proposed/STT_6_rmwjmp.als). parsexml.py and the instruction
tables are approval-gated: Anna signs off before any of this is applied.

WHY IT IS NEEDED: today's parsexml maps unknown kind tags to "unknown" -> other_n, so
an RMW XML is SILENTLY concretized as an ALU op (scratch run: the RMW transmitter at
pc2 became `leaq ($1,$2),$0`, and ann.json said "kind": "unknown"). Never feed
STT_6_rmwjmp XML through the unpatched pipeline.

WHAT IT DOES
  - _TYPE_TAG_TO_KIND: TRmw -> "rmw", TJump -> "jmp".
  - instructions.jsonc: categories rmw/jmp; candidates
      rmw_or     uses [inreg0, inaddr, inmem, outmem]   -> `orq src, (addr)`
      jmp_direct uses []                                -> `jmp .Ljmp_<stem>_pc<N>` to the next instruction
  - pass 5 (emit): new `rmw_or` branch. Addressing is the same as `load`/`store`:
    specified inaddr -> `orq src, (%probe_base, %inaddr, 1)` (probe_mem + secret);
    otherwise `orq src, off(%mem_base)` using the outmem (= inmem) slot. src = the
    inreg0 SSA value pinned to its physical register; a blank inreg0 gets a pass-3
    virtual register initialised to 0, so the RMW is value-neutral. The pc marker
    (and the last_committed/first_noncommitted labels) are inside the same asm
    string, directly on the orq, so ann.json xmit.pc = the RMW.
  - pass 5: new `jmp_direct` branch: `<marker>jmp .Lj; .Lj:` in ONE inline asm, so the
    LLVM CFG is unchanged, nothing can land between marker and jmp, and the jmp is
    a real direct unconditional transfer to the next instruction. No branch
    annotation, no BTB force (pass 2.5 only rewrites br_n/br_x; jmp is not in
    _BRANCH_KINDS, so it is untouched there).
  - probe_mem allocation check: add "rmw_or" next to "load"/"store".
  - _stl_arch_values (stl_bypass only): rmw_or = mem[a] |= src; jmp_direct = no-op.
    Note pass2_6 STL pairing still looks only at kind "str"/"ld", so an RMW is never
    an STL store/bypass-load partner; that would be a separate change.

NOT IN THIS DIFF (also approval-gated; listed so nothing is forgotten)
  - pipeline.py _KIND_TO_CHECKER: add `"rmw": "check_ld.py"`. Today "rmw" already
    falls back to _DEFAULT_CHECKER = check_ld.py, so behaviour is the same, but the
    mapping should be explicit. check_ld sees the RMW's ldst micro-op as an LSQ
    "Executing load" (VOCAB_TABLES.md "RMW agent findings"); the data-obtained gate
    applies unchanged. testrun.py partitions by kind, so RMW hits would land in a new
    `<mode>/rmw/` dir; dashboards that hard-code ld/br_x/other_x need the new kind.
  - interleave _build_chain (parsexml.py:307-331) does not inject rmw/jmp steps.
  - pass 2.5's mispredict_taken ftbypass trampoline was not exercised with a jmp in
    the program (only mispredict_not_taken was tested).
  - On CleanupSpec every speculative RMW hits the known UV3 (cleanup_skip nohitinfo),
    so a diag_uv3_rmw known-cause bucket must exist before running there.
