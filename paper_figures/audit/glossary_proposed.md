# Proposed glossary (term audit, 2026-11-03)

Source: paper snapshot (commit 5565656), compiled files only (sections via the \input chain, plus every tikz figure/table they input). Checked against `STAGE1_alloy/models/STT_6.als`, `STAGE3_gem5/check_ld.py`, `pipeline.py`, `paper_figures/FIGURES.md` (glossary), `URGENT_TODO.md`, and the STT, AMuLeT, SPT and ReCon papers in `~/Documents/quail/sources/papers/`. "Rec." marks a recommendation; the naming decisions are Anna's.

| Term | Proposed definition | Where it is first used | Inconsistent spellings / uses found |
|---|---|---|---|
| Execution contract | The part of a defense specification that says which instructions are speculative (STT: uncommitted, with an older unresolved branch). | model.tex:2 (defined :7) | "speculation contract" in Table I caption, Fig. 3 slab 3a, discussion.tex:5, `.als` `speculation_contract_p`. Anna prefers "execution contract"; the figures and table still need changing. |
| Leakage contract | The set of (instruction kind, operand) pairs the defense treats as transmitting (STT: load address, Branch_x condition). Unlike Guarnieri-style contracts, it has no observation clause. | model.tex:2 (defined :5) | "leakage function" (Fig. 3 slab 3c, Table I, discussion.tex:5, `.als`). related.tex:27 uses "leakage contract" in the prior-work sense. intro.tex:21 calls that prior-work object a "security contract". pipeline.tex:128 adds "leak contract". |
| Protection set | The architectural state (registers, memory) the defense promises not to leak, plus an update rule giving how each instruction changes it. | background.tex:3 (defined model.tex:9) | "protected state + propagation" (Fig. 3). The STT example (model.tex:29) omits the update rule that Fig. 2's caption uses. results.tex:137 says "a transmitter ... in the protection set", but the set holds state, not instructions. |
| Protection-set update rule | How one instruction adds state to or removes state from the protection set (STT: a load with no older unresolved branch removes the location it reads). | model.tex:9 | "propagation" (Fig. 3, `.als` `prot_set_propagation_p`). The violation definition says "as updated by the most recently committed instruction", but the code applies the rule over every instruction in spo order. |
| Leakage predicate | The per-defense formula built from the three components; an execution graph violates it when the condition under "violation" holds. | model.tex:11 | It is defined a second time, in different words, as "violation" at pipeline.tex:23. pipeline.tex:128 calls it "leak contract". |
| Violation | (Model only.) A data-dependence path from protected state to an operand in the leakage contract whose instruction is speculative under the execution contract. | intro.tex:11 (defined pipeline.tex:23) | Also used for the gem5 checker verdict (pipeline.tex:99,104; Fig. 6) and for AMuLeT's "contract violation" (results.tex:156). |
| Hit / leak | Hit: a gem5 run whose transmitter transmits inside the violation window. Leak: a hit that passes the data-obtained gate. | pipeline.tex:83 ("violating hit") | "real leak", "confirmed real leak", "violation". Rec. (FIGURES a7): violation, then hit, then leak. |
| Transmitter | An instruction one of whose operands the defense's leakage contract says can leak through a side channel. | intro.tex:3 | Defined three times (intro.tex:3, background.tex:3 "create data-dependent behavior", model.tex:5). pipeline.tex:20 makes it an instruction kind (Load, Store, Branchx, Otherx), but under STT, Store and Other_x never transmit. |
| xmit / target transmitter | The one transmitter per test that the model flags (`isxm`) and the checker watches. | Table I (execvocab), pipeline.tex:99 | Consistent. Keep "xmit" for figure labels and code. |
| Instruction kinds | Load, Store, Branch_x, Other_x (may transmit, as the leakage contract decides); Branch_n, Other_n (never transmit). | Table I; pipeline.tex:20 | pipeline.tex:20 spells them Branchx/Otherx/Branchn/Othern. Code: TBranchx etc. |
| Transmission mechanism | For one transmitter kind, the pipeline event by which it transmits (e.g. a load's cache access or a store-to-load forward), which the inspector detects. | Fig. 3 node (decided by Anna) | "transmission criterion/criteria" (Fig. 3 caption, Fig. 6 node and caption, results.tex:87), "Transmission Requirement" (heading), "per-transmitter pipeline predicate", "signal". |
| Inspector / checker | The inspector runs one checker per transmitter kind (check_ld / check_br / check_other); each applies that kind's transmission mechanism to the gem5 trace. | Fig. 3 ("Inspector"); pipeline.tex:89 ("checker") | "test validator harness" (intro.tex:23), "validator" (abstract, where it also generates tests). |
| Execution graph | A finite graph of instructions in spo, with operands, state and rf/ddi edges, plus committed/resolved/xmit flags. | background.tex:11; model.tex:2 | "abstract execution", "abstract execution graph", "instance" (Alloy solution), "test" (pipeline.tex:20). results.tex:80 uses "instances" for race hit counts. |
| Observation time | The tick at which the transmitter transmits. The graph's committed/resolved flags describe each instruction at that tick, so an instruction flagged committed may have been speculative earlier. | pipeline.tex:71 (also "time snapshot", :15) | Never defined. The interleave and OTB captions call committed i0/i1 "speculative", which only makes sense with this definition. |
| Resolved / unresolved | A branch is resolved once its direction and target are known; a store is resolved once its address is known. The flag is meaningful only for branches and stores. | pipeline.tex:20 | Never defined. Table I lists it as a Boolean on every instruction. Called "Booleans" in Table I and "flags" in the text. |
| Committed | The instruction has retired by the observation time; this implies resolved. | Table I; pipeline.tex:20 | "retired" in figures and gem5 ticks (fine for gem5 times). |
| Speculative / transient | Speculative: the execution contract says the instruction is not yet safe. Transient (wrong-path): speculative and on a mispredicted path, so it will be squashed. | intro.tex:3 ("transient") | "wrong-path" (results), "mis-speculated path" (pipeline.tex:104), "modeled path". |
| lc / fnc | lc: the youngest committed instruction. fnc: the oldest uncommitted instruction. The commit boundary lies between them. | pipeline.tex:86 ("fnc-stall"; defined only at :104) | "first non-committed" (text, Fig. 6) vs "first uncommitted" (Table II, code `first_uncommitted`). "speculation boundary" (pipeline.tex:92) for fnc is wrong under STT. RC says "last-uncommitted". |
| spo | Speculative program order: the processor's fetch order, including instructions on a mispredicted path. Unlike MCM po, it can contain instructions that never commit. | pipeline.tex:30 | "total program order" (pipeline.tex:20). Background introduces po only. |
| rf | Reads-from: links an output operand to a later input operand naming the same register or memory location (it generalizes the MCM rf to registers). | background.tex:11 (MCM sense); pipeline.tex:20 | Background's MCM rf relates memory write to read. Not expanded at pipeline.tex:20. |
| ddi | Data-dependence internal: links an input operand to an output operand of the same instruction. | pipeline.tex:20 | Expanded only in Table I and the Fig. 2 caption (decided name). Not expanded at first prose use. |
| Relaxation (RI/RO/RS/RC/RR) | A one-step change to an execution graph: remove an instruction, operand or state element; mark fnc committed (RC); mark an unresolved instruction resolved (RR). | background.tex:11 | "removed or demoted" (background), "removal or weakening" (pipeline.tex:31), "perturbations" (pipeline.tex:41; code PTag). RC is misdescribed ("last-uncommitted"). Only RR, RC+RR and RS are checked in gen_useful_litmus (URGENT_TODO DECIDE). |
| Minimality | A violating graph is minimal if every relaxation of it is non-violating. | background.tex:11 | "minimality requirements" vs "minimality criterion/criteria". |
| Leakage backbone | A minimal violating execution graph. Use "leak path" for the data-dependence path inside it. | pipeline.tex:15 (defined :37) | "leakage path skeletons" (intro.tex:29), "leakage path structures" (intro.tex:31), "leakage path forms" (pipeline.tex:6), "forms of leakage", "LB" (statetable). Used both for the whole graph and for the path. |
| Stage 1 / 1.5 / 2 / 3 | 1: bounded-exhaustive Alloy enumeration of backbones. 1.5: non-exhaustive Alloy interleaving (relaxations loosened, Stage-1 graph pinned). 2: concretization into x86 plus annotation. 3: gem5 execution under the harness, plus the inspector. | Fig. 3; pipeline.tex:63 (Stage 2) | The text never says "Stage 1" or "Stage 1.5". Fig. 3 calls 1 "Abstract test generation" and 1.5 "Abstract test enumeration", which inverts Anna's decided exhaustive/non-exhaustive wording. |
| Alloy interleaving (Stage 1.5) | Re-running Alloy with some relaxations turned off and each Stage-1 graph pinned, so tests can include extra instructions that share the backbone's state. | pipeline.tex:54 | "Overlapping interleaving" (heading), "first round of instruction interleaving" (:58), "Alloy interleave" (statetable). |
| Concretization interleaving (Stage 2) | Pass 4: inject 1-2 synthetic chains after the commit boundary. Their operands come from the free pool, so a chain can feed an unspecified backbone operand. | pipeline.tex:58 | "second round of interleaving" (:78), "Stage 2 interleaving", "step 4". pipeline.tex:58 says this round handles "non-state-sharing instructions", which contradicts :78. |
| Free pool | The registers and memory slots not tied to an Alloy state atom. Every unspecified operand and every chain operand draws from it. | pipeline.tex:78 | "reserved register pool" (Fig. 4 caption) is the opposite set (reserved = tied). "step" vs "pass" for passes 4 and 5. |
| Annotation | The per-test `.ann.json` that Stage 2 writes: element PCs, each branch's mode and BTB target, the xmit's kind, store-bypass PC pairs. | intro.tex:26 | pipeline.tex:15 uses it for the graph's flags. Also "speculation annotations" (intro.tex:27), "committed annotations" (pipeline.tex:83). |
| Directive | One thing the annotation (or run config) asks gem5 to do: force a prediction, hold a resolution, stall commit. | pipeline.tex:15 | "simulator directive", "speculation and timing directives". Timing values come from the run config, not the annotation (claudenote :89). |
| Hook | A gem5 source site that carries out a directive (BTB-forced target, resolve stall, commit stall). | pipeline.tex:86 | "control hooks", "config glue", "observation"; "selects hooks" (Fig. 3). |
| Probe | An existing gem5 debug trace (O3PipeView, LSQUnit, Commit) that the inspector reads. | Fig. 3 | "observation" (pipeline.tex:86). |
| Harness / non-invasive | Harness: the hooks plus the probes. Non-invasive: it changes prediction and timing only, never the defense's protection logic. | intro.tex:23 | "test validator harness", "gem5 harness". "non-invasive" is undefined even though the hooks change prediction and timing. |
| BTB-forced target | A hook that overrides the branch target buffer (BTB) prediction at an annotated branch PC. | pipeline.tex:89 | BTB is never expanded; "branch force", "force", "branch-annotation". |
| Stall knobs s_R / s_U / commit stall | s_R: resolve delay of a correctly predicted branch. s_U: how long an unresolved branch or store is held unresolved. Commit stall: cycles fnc is held at the ROB head. | pipeline.tex:72 | "per-branch resolve-stall", "resolve delay", "resolved-branch stall"; "unresolved-branch stall", "long stall", "5000-cycle resolve stall"; "fnc-stall", "commit-stall", "fnc-commit-stall", "fnc stall". |
| Violation window | The interval (lc_retire, fnc_retire) during which every branch the model marks unresolved is still unresolved (R1 decides whether it ends at resolution). | pipeline.tex:99 | "committed window" (pipeline.tex:99,104; race fig), "unresolved window" (Fig. 6), "speculative window" (results.tex:125,147,166; pipeline.tex:92), "commit window" (discussion), "leak window" (pipeline.tex:128). Table II row 4 omits the unresolved gate. |
| Window-valid | (AMuLeT corpus analysis.) A real register chain links a speculatively loaded secret to a transmitter, and the speculation window provably outlasts the transmitter's act. | results.tex:134 | Undefined in the paper; "leaky load/branch" (results.tex:135). Source: wiki/results/PAPER_RESULTS.md:346-362. |
| Speculation primitive | A hardware prediction (e.g. branch prediction, memory-dependence prediction) that an instruction triggers and that starts speculative execution. | model.tex:7 | discussion.tex:13 uses it for what gem5 implements, not for what the defense considers. pipeline.tex:70 says Table II lists primitives, but the table also lists the commit boundary and the transmitter. |
| Store bypass | The data-flow speculation primitive: a load mispredicts no alias with an older, unresolved store to the same address and reads stale memory. | pipeline.tex:75 | "store-to-load forwarding misprediction", "STL" (Fig. 3 pass 3), "store bypass" (Table II), "store-to-load forwarding done" (discussion), "store set" (pipeline.tex:92, Fig. 4 caption, undefined). |
| Store-to-load forwarding (STLF) | The load receives an older in-flight store's value from the store queue. This is the ReCon bug's path and check_ld's store_forward leak. | pipeline.tex:89 | Conflated with store bypass. "Store-to-load forwarding bypass" (results.tex:20). Code: SLF, STLF. |
| Taint / untaint | STT's (and ReCon's) run-time marking of values derived from speculative loads. It is the defense's implementation of the protection set; untaint clears it when the load reaches its VP. | background.tex:3 | Glossed only as "tainted, or secret". model.tex:22 puts 'tainted' in straight quotes. "untaint" is undefined. |
| Visibility point (VP) | The point at which the defense no longer considers an instruction speculative (STT Spectre model: all older branches resolved; STT Sec. 6.1). | intro.tex:31 | Never defined. "VP" is unexpanded (results.tex:130). The race has about six names. |
| VP/squash race | STT/SPT clear a transmitter's protection at branch resolution, before the squash reaches the load queue, so the wrong-path transmitter touches the cache. | intro.tex:31 | "visibility-point--squash timing race", "visibility-point/squash race", "visibility-point<->squash race", "VP<->squash race", "the STT race". |
| ReCon | The defense of Aimoniotis et al. (MICRO'23). "ReCon-STT" = its gem5 implementation of STT. | intro.tex:31 | "Recon", "Recon-STT" in all figures/captions, results.tex:20, discussion. "gem5-recon-modded", "/work/gem5-recon" appear in captions. |
| HSCA / HSCD | Hardware side-channel attack / defense. Rec.: use "Spectre defense" in prose, or expand HSCD at first use. | intro.tex:3 (HSCA); background.tex:3 (HSCD) | HSCD never expanded; "SCDs" (background.tex:6), "HSC leakage" (intro.tex:31). |
| Defense acronyms | STT = Speculative Taint Tracking; SPT = Speculative Privacy Tracking; DoM = Delay-on-Miss; SPT-Fence = SPT run with its SpectreSafeFence gem5 scheme; scheme = gem5 `--scheme` variant (Unsafe, Delay, STT, DoM on the ReCon build). | abstract; intro.tex:31 | STT expanded only at background.tex:3 and model.tex:22. SPT, DoM, SPT-Fence and "scheme" are never expanded. SPO is never expanded or cited (I could not find what it stands for, unverified). |
| UV / KV | AMuLeT's bug labels: Unknown Vulnerability / Known Vulnerability n (AMuLeT Sec. 4). | results.tex:21 | Never expanded. |
| Defense block | (Rec.: drop it.) Table I's word for the three defense components. Say "the three defense components" instead. | Table I caption | Undefined. "defense unit" (specs/) is not in the paper; keep it out. |
| Litmus test | In SimSpect, a pair: an x86 program and its annotation. | abstract | intro.tex:11 says a litmus test "can only specify architectural behavior", which conflicts unless the pair is defined. |
| Instruction bound | The number of instructions in each Alloy instance (exactly 6 in the runs; smaller graphs appear only padded with Branch_n). | intro.tex:23 | "size bound", "up to a bound". The models use `exactly 6 Instruction`. |
