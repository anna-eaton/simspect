## What exists

`tikz/interleave.tex` is a one-column `figure`, `\input` at `sections/pipeline.tex:33`, inside the subsection "Overlapping interleaving" (`pipeline.tex:31`), which describes the *Alloy* round of interleaving (`pipeline.tex:34`). It draws a six-instruction abstract program. I0 `branch_n` and I1 `load reg0 <- mem 0` are drawn in blue as the two added instructions. I2-I5 are the backbone of `fig:ddi-rf` (`tikz/alloyviolation.tex`), renumbered. Edges: ddi `mem 1 -> reg1` (I3) and `reg1 -> reg2` (I4); rf `I3.reg1 -> I4.reg1`, `I4.reg2 -> I5.reg2`, and `mem 0 -> I4.reg0`. Flags: I0 and I1 `r c`, I2 none, I3-I5 `r` (the source comment at `interleave.tex:68` says r = resolved, c = committed). Caption: "Adding two instructions in the Alloy interleave phase allows complication of a test that will later exhibit a leak due to erroneous 'taint tracking' mechanism in gem5, due to the additional branch resolving and unprotecting reg2 because of the shared data dependency in the ALU op on reg1 and reg0, when reg0 should still be protected."

Rendered problems (`paper_figures/drafts/audit/audit_interleave.png`): blue for the added rows; 10 pt Courier body and 9 pt edge labels (the language says 8 pt / 7 pt); bold flags; `Stealth` arrows, `semithick`; uneven row pitch (0.7 to 0.95 cm, about 20 to 27 pt); the rf arrowhead lands on `reg0` with the `r` flag touching it; the `I3 -> I4` rf diagonal crosses `reg1` and the `ddi` label; the `rf` label sits on the ddi arc.

## What changes in v3 (content kept)

- **Same program, flags and edges**, with one flagged correction (D2 below).
- **Black only.** The blue is gone; the added rows are marked by a left bracket and a 7 pt italic label "added by interleaving". Gray is not used, because gray means defense-specific in this paper.
- **Fonts.** Listing in `\footnotesize\ttfamily` (8 pt, Courier in the paper). Flags in 8 pt roman, not bold. Edge labels, the bracket label and the key in `\scriptsize\itshape` (7 pt). Nothing smaller than 7 pt. Hyphenation off in nodes.
- **Character grid.** Every token sits on a column that is a multiple of one typewriter character, so opcode, destination, arrow and source line up across rows. Uniform 13 pt row pitch.
- **Edge convention.** An arc above a row is a ddi edge (inside one instruction). A line routed through the gaps between rows is an rf edge (from an output operand to a later input operand). The long rf from I1 runs down a rail to the right of every row and enters `reg0` from the right. No edge crosses text or another edge.
- **Labels.** `ddi` on the I1 and I3 arcs and `rf` on the long rail; the short edges follow the same visual convention. A key line "r = resolved, c = committed" sits top right (from the source comment at `interleave.tex:68`; the original never explained r/c).
- **Code.** `TUNING KNOBS` block (pitch, columns, arc heights, rail position), `>=latex`, default line width, sharp corners on the memory boxes.

## Content check against the code and notes

Sources read this session: `wiki/design/CONCRETIZATION_PASSES.md`; `STAGE2_compilation/parsexml.py:170-335` and `1255-1395`; `wiki/findings/mdsToRead/OTB_GENERATION_GAP.md`; `wiki/results/reconresults.md` Bug 1; `specs/alloy_models.json`; `STAGE1_alloy/models/MANIFEST.md`; `STAGE1_alloy/models/STT_6.als:81-82, 155-174`; `claudelog.md:49-51, 999-1008`; the three interleave run configs.

- **M1. The caption says "Alloy interleave phase", and the figure sits in the Alloy-round subsection, but the model used for that round cannot emit this program.** The program's key feature is a two-source merge at I4: reg1 comes from I3 and reg0 from I1. `STT_6` has RI and RO off (`MANIFEST.md`, "Minimality relaxations ON: RR + RC + RS; OFF: RI + RO"), which is what `pipeline.tex:34` calls the first round. Yet `specs/alloy_models.json:15` says STT_6 "STRUCTURALLY CANNOT emit a two-source (in-degree>=2) merge". Anna's 2026-10-30 decision (`claudelog.md:49-51`) puts OTB in "the second (interleave) stage ... via `parsexml:pass_interleave`".
- **M2. If the figure shows the concretization round (`pass_interleave`), four details disagree with the code.** (a) Chains are built only from `other_n`, `ld` and `str` (`parsexml.py:173`, `_build_chain` 304-332); `pass_interleave` never inserts a branch, so I0 cannot be an added instruction. (b) Chain steps go only after the first uncommitted instruction (`parsexml.py:1319-1358`), but I0 and I1 are drawn before the backbone and marked committed. (c) Chain steps carry `resolved: False, committed: False` (`parsexml.py:200-201`), so they would have no r/c flags. (d) Every interleave config uses chains of 2-4 steps (`chain.min_length: 2` in `runconfigs/run_config_STT_6_interleave_j12.jsonc`, `run_config_STT_all.jsonc`, `run_config_otb_probe.jsonc`), not one load. OTB_GENERATION_GAP.md also says "Only `ld_inj` comes from interleave; the base Alloy must emit `br_r … br_u ld_base other xm`".
- **M3. The hook onto I4's second operand happens in pass3, not in interleave.** The backbone's `other` has a legitimately unspecified second operand (OTB_GENERATION_GAP.md, "Why it's absent", point 1). The chain's register lands on it only because pass3 draws unspecified slots from the same free pool as the chain atoms (`parsexml.py:266-272`; CONCRETIZATION_PASSES.md §2, item 6). The figure shows `reg0` already named in I4, and in `fig:ddi-rf` too.
- **M4. The original rf edge for reg0 is ill-formed in the model.** It starts at `mem 0`, I1's *input* memory operand. In STT_6, rf runs only from an output operand to an input operand (`STT_6.als:156`) of the same state (`STT_6.als:159`). Fixed in the draft (D2).
- **M5. The caption names the wrong register.** "When reg0 should still be protected" should be reg1. reg1 comes from I3, under the still-unresolved younger branch I2; reg0 comes from I1, whose older branch I0 resolves (`reconresults.md` Bug 1, Summary and Timeline steps 3-6; the `tikz/otbtwobranch.tex` caption says the same).
- **M6 (minor). The abstraction level doesn't match the moment interleave runs.** By the time `pass_interleave` runs, pass2 has already chosen concrete instructions (`other_n` becomes `add` or `bitnot`) and pass2_5 has set branch primitives (CONCRETIZATION_PASSES.md §2, items 2-3). The figure uses Alloy kinds (`branch_n`, `other_n`). Registers are still abstract, which is right, because pass3 assigns them after interleave. This is acceptable for a conceptual figure, and no change is proposed.
- **Related, not in this figure:** `pipeline.tex:43` describes the second interleave round *after* "we then reserve those state locations, and randomly allocate the unspecified operands", but in code `pass_interleave` runs before pass3, which does all physical assignment (CONCRETIZATION_PASSES.md, Summary). The pipeline figure's Stage-2 list order has the same issue (CONCRETIZATION_PASSES.md §8).

Adding it means rerouting the I4 rf edges, because an arc from `reg0` to `reg2` passes over `reg1`, where the I3 rf lands. *Recommendation:* add it if D1 = (a) or (c); under (b) the merge is concrete (`add` reads both inputs), so this is moot.

Typewriter for abstract instructions.** VISUAL_LANGUAGE allows typewriter only for literal code. v3 keeps `\ttfamily` for the listing, because the opcodes are literal model kinds and the column grid relies on monospace.
