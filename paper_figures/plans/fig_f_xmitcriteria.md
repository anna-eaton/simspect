## Gaps found

1. **STT and Recon have no criterion JSON.** `stt.json` / `recon.json` are leakage-contract stubs (transmitter list + checker name). The load criterion for both lives only in `check_ld.py` code plus prose in `transmitter_criteria.json` `kinds.ld`, and the stubs' `checkers` field is not read by the pipeline (`pipeline.py:296-314`; known, `specs_jsons.md:13`). This is the main asymmetry the table shows.
2. **Recon gate bug** (`recon_cache_reach_gate/README.md`, not fixed): on Recon-STT `reached_cache` can never fire, so squashed-before-complete real sends are scored non-leaks.
3. **The data-obtained gate is not time-bounded.** The window is tested on the `Executing load` tick; `_xmit_cache_fate` only asks whether some dynamic instance at that PC ever sent a packet or completed (`check_ld.py:56-75`, no tick comparison), while the code comment (`check_ld.py:117`) and `transmitter_criteria.json` say it "OBTAINED its data in the window". Partly noted in `NEAR_MISS_BREAKDOWN.md:38` ("G is evaluated independently of the window"). Execute tick is the max over instances (`check_ld.py:30-36`), fate is any instance.
4. **Footprint criteria are not transmitter-specific.** `check_footprint.py` ignores `xmit_pc`; any squashed instruction younger than lc is an actor (open DECIDE, `URGENT_TODO.md`, "DECIDE: InvisiSpec footprint checker").
5. **No reported result was produced under the JSON criteria** (table above). The legacy checkers differ from the JSONs in substance: `check_ld_speclfb.py` requires SpecLFB's own `isUnsafe=0`, while `speclfb.json:98` says "spec is the paper's definition, not SpecLFB's isUnsafe flag"; `check_ld_cleanupspec.py` gates on `t < load_squash_tick` (`check_ld_cleanupspec.py:121-123`), unlike check_ld's "squash timing NEVER gates"; the compound and cleanupspec checkers bypass the execution-validity gate.
6. **Registry disagrees with the criteria.** `specs/gem5_builds.json:157,188,217` still names the legacy checkers as each AMuLeT build's checker, while `specs/leakage/*.json` name `check_footprint.py`; `defense_units.json` points units 4/6/7 at the JSONs whose results do not exist yet.
7. **`check_footprint.py` can hide leaks** (audit, `claudelog.md:94`; `URGENT_TODO.md` "DECIDE: C-1..C-5"): events with `seq=-` or attributed to a committed instruction are dropped (`is_actor(None)` is False, `check_footprint.py:216-218`), and the window is tested on the event tick. Still true in the current code.
8. **Build and hook status:** amulet-InvisiSpec's current binary panics on every run (`specs/gem5_builds.json:166`); SpecLFB's `LFB` hooks have never fired in a verification run (`SIMSPECT_HOOKS.md:102`; `speclfb.json:141-143`); CleanupSpec hooks are incomplete (`claudelog.md` 2026-10-28 audit item 2).
9. **`requires.gem5_args` is read by nothing** (`claudelog.md` 2026-11-02 bigfig-audit item 4), so a run without `--ruby` / `--l2cache` would be judged by a criterion whose structures it never exercises.
10. **Stale docs:** `transmitter_criteria.json:7` calls `Executing load` the "cache touch", which is wrong on Recon-STT (delay unit after it) and on InvisiSpec (invisible spec read). `transmitter_criteria.json:26-28` and CLAUDE.md say check_br lacks the window, but `check_br.py:85-99` enforces it (`claudelog.md:17`). CLAUDE.md "Leak criteria" describes only `check_ld`/`check_br`, not the footprint criteria.

## Where the paper text disagrees (paper is read-only; for Anna)

- `sections/pipeline.tex:63` describes the load signal as LSQUnit ticks "(… on newer builds an additive `memaccess` tick for SpecLFB and an `expose` tick for InvisiSpec)". Those are the legacy checkers (`check_ld_speclfb.py`, `check_ld_invisispec.py`); the JSON criteria use SimSpect cache-event hook lines instead.
- `pipeline.tex:55, 90` say detection reads only the existing `O3PipeView`, `LSQUnit` and `Commit` streams and that "No cache or defense code is instrumented to *see* a leak". The footprint criteria read SimSpect print hooks added to the cache code (`SIMSPECT_HOOKS.md`), and every row's window uses the BR resolve hook lines.
- `pipeline.tex:57`: "all branches guarding the transmitter are still unresolved". The gate is the model's unresolved branches, at `resolve_visible` (same note as fig d).
