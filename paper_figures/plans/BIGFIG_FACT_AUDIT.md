# Pipeline figure fact audit (`_standalone_pipeline_vertical_8pt`)

*Written 2026-11-02 by a read-only audit agent. Figure source: `paper_figures/drafts/_standalone_pipeline_vertical_8pt.tex`; `tex:N` below means a line in that file as of this audit. The audit covers the current text plus the upcoming wording Anna listed (marked "upcoming"). Nothing was edited except this file, `claudenotes.md`, `claudelog.md` and one line in `URGENT_TODO.md`; no `.als`, `parsexml.py`, gem5 hook, figure `.tex` or paper file was touched, and no git write was run. Every verdict cites a file:line read this session. The one non-repo source is the bundled Alloy jar, inspected with `unzip` and `javap`.*

## Summary

The figure describes the **target two-stage design**, not the pipeline that produced the reported results. Stage 1.5 exists only as an STT prototype (`STAGE1_alloy/stage_pipeline.py`, `stage_seed.py`, `models/STT_6_core.als`), wired into nothing, and no campaign used it. Every reported result comes from one flat Alloy enumeration (RR+RC+RS minimality, capped at `max_instances`). The two "exhaustive" claims are unsupported: no production enumeration has ever reached UNSAT, and the prototype's Stage 1 stops on a timeout. Two claims are wrong or unsupported in a way readers would notice: Stage 2 has no C++ (it is Python plus the LLVM toolchain), and no code passes the transmission mechanisms into the gem5 harness. Several defense-specific inputs are missing from the shading: the run config (scheme, threat model, stalls, checker), and three of the seven finished defense units have no Alloy spec of their own (they reuse `STT_6`). The Stage 2 pass list matches `wiki/design/CONCRETIZATION_PASSES.md`, with two small wording issues in passes 1 and 5.

Verdict counts (43 rows): 25 correct, 13 imprecise, 1 wrong, 4 unsupported.

## Decisions for Anna

- **D1. What does the figure describe?** Option A: keep Stage 1 → 1.5 as the method, label Stage 1.5 an STT prototype, and say in the text that every reported result used a single flat enumeration. Option B: redraw with one Alloy stage (RR+RC+RS, capped), matching the evaluated system. Option C: run the staged pipeline for at least one reported campaign before submission. Evidence: rows 10, 7; `STAGED_ENUMERATION.md:90-91`; `MANIFEST.md:11-17`. **Recommendation:** B, unless you commit to C. A main pipeline figure that no result went through will draw a reviewer question.
- **D2. "Exhaustive" (rows 7, 9).** This is `PAPER_PLAN.md` D1. Option A: say "bounded enumeration (≤ 6 instructions)" now. Option B: run EXP-1 (cores to UNSAT at bound N) and then say "exhaustive up to N". **Recommendation:** A for this draft.
- **D3. Are clauses 1-2 really shared?** `rf_from_most_recent_writer` is missing from Recon_6 and SPT_6_oneLP (already a DECIDE item). New in this audit: SPT_6_oneLP also changes the leak clause to exactly-one-leak-point (`SPT_6_oneLP.als:268-274, 314`), and its operand-typed protection set changes skeleton code. Option A: align the models (`.als` changes plus a regen). Option B: say "shared skeleton, with these per-defense exceptions" in the text. **Recommendation:** B for this deadline.
- **D4. Stage 1 minimality: RO+RI or RI-only** (`URGENT_TODO.md:100-108`). The clause 2 wording depends on it: "every instruction and operand is needed" (RO+RI, which loses the br_x-gate mechanism) vs "every instruction is needed" (RI-only, which rebuilds the in-use set exactly at N=3). **Recommendation:** as in TWO_STAGE: RI-only if Stage 1.5 is meant to reproduce in-use.
- **D5. The footprint defenses reuse `STT_6`.** SpecLFB, InvisiSpec and CleanupSpec (and the to-run Delay/DoM) have no Alloy spec of their own (`specs/defense_units.json:18, 26, 30`), so "defense specification → clause 3" is not per-defense for them. Option A: say so in the text (they share STT's speculation and protection contract and differ only in the transmission mechanism). Option B: write per-defense models. **Recommendation:** A.
- **D6. The transmission → harness arrow (row 39).** Option A: drop it. Option B: relabel it "design time". Also consider an arrow from the defense specification to the transmission mechanisms, since the transmitter set is written in both places. **Recommendation:** drop the harness arrow and add "from defense spec" to the mechanisms label.
- **D7. Shading the run config (rows 29, 41).** Option A: rename the box "Defense build + config under test". Option B: add a separate shaded run-config input that also feeds the timing directives. **Recommendation:** A. It costs nothing in width and covers scheme, threat model and stalls.
- **D8. "Non-invasive" (row 30).** Option A: replace it with "minimal harness (defense logic untouched)". Option B: keep "non-invasive" and add a caveat in the text that the directives change prediction and timing by design. **Recommendation:** A.

Mechanical fixes that need no decision: Stage 2 "(Python, LLVM)" (row 20), the pass 1 and pass 5 wording (rows 22, 24), "one pair per branch mode × interleave variant" (row 27), the probe list (row 31), and the annotation arrows (row 37).

## Limits of this audit

- gem5 source lines were not re-read: cafe2 was not contacted. Hook behaviour is taken from the repo's hook docs and captured diffs (`RESOLUTION_HOOKS.md`, `SIMSPECT_HOOKS.md`, `gem5-hooks/README.md`), which record their own verification runs.
- I did not check whether Kodkod's symmetry breaking can drop non-isomorphic instances. That question matters only if the figure claims exhaustiveness at all (D2).
