# Post-hoc graph checker: deciding the Alloy leak condition on a concretized program (design, 2026-11-08)

Session graph-checker. Design only, plus a small prototype. Nothing in the pipeline, no `.als`, `parsexml.py`, gem5, hook or spec file was changed, and there were no git writes. Anna's idea (claudelog 2026-11-08 ~21:15): take a program Stage 2 has already turned into real x86 and check the Alloy leak condition on it directly, the way herd evaluates a memory model on a concrete execution, so Stage-2 insertions (splices, fillers, xmm routing, store separation, OTB merges, new vocabulary) can be validated after the fact instead of by hand or by re-running Alloy. Line numbers for `parsexml.py` are as of 2026-11-08 ~22:00; another session is editing that file, so they drift.

## TL;DR

- **Recommendation: "Alloy as the evaluator" (option c, in its no-search form).** Build the program's execution graph, write it out as an Alloy *instance* XML, and have Alloy evaluate the model's own `secure_speculation_scheme_p[no_p]` on it with `A4SolutionReader.read` plus `A4Solution.eval`. That is Alloy's built-in evaluator, not a SAT search. It needs no port of the defense semantics, so the `.als` stays the single source of truth. Measured: about 23 ms per program for STT_6 and 4 ms for STT_6_v2, after a 110 ms model load. For SPT, the fold has to be iterated by the harness (one step per `eval`), because the nested expression costs 21 s per program and the unrolled one runs out of memory.
- **The hard part is the graph builder, not the semantics.** Turning x86 into Alloy's rf/ddi/spo vocabulary has real modelling choices (two-register addresses, flags, micro-op splits, the prologue). Those choices are where faithfulness can be lost, and several of them are decisions for Anna.
- **Two traps in using the `.als` directly, both measured.** (1) The protection-set fold is hard-coded to 7 steps (`STT_6.als:232-243`), so any program with more than 7 instructions has to have the fold unrolled by the harness. For SPT this changes answers. (2) The model's facts mix three things: well-formedness, vocabulary bounds and generation-only constraints. A checker must evaluate only the first group.
- **The existing hand-port `mf_semantics.py` is the fast cross-check, not the source of truth.** It agreed with Alloy on every STT case tested and runs in about 0.1 ms per program, but it covers STT and Recon only and drifts whenever a model changes.

## 1. What the checker has to model

### 1.1 The leak condition, defense by defense

Every model is the shared skeleton plus a three-clause defense block (CLAUDE.md "Alloy model structure"). At the unperturbed point `p = no_p` the leak condition is `not secure_speculation_scheme_p[no_p]`, and a generated test additionally has the designated transmitter flagged (`tag_xm`, `STT_6.als:270-273`). Written out:

- **Speculation contract.** `speculation_contract_p = uncommitted_p & has_unresolved_brs_p`, i.e. uncommitted and after an unresolved branch in `spo` (`STT_6.als:325`, `:245-247`). It is the same in Recon_6, SPT_6_oneLP_v2 and the proposed `STT_6_v2` (`SPT_6_oneLP_v2.als:369`).
- **Leakage function.** STT/Recon: `Loads.inaddr + Branchxs.inreg` (`STT_6.als:328`). SPT v2 also counts `Stores.inaddr` (`SPT_6_oneLP_v2.als:378`). `speculative_xmit_p` is the leakage operands of speculative instructions (`STT_6.als:229`).
- **Protection set, a fold over program order.** `last_committed_protset_p` folds `prot_set_propagation_p` over `f, f.spo, …, f.spo^6` starting from `hardware_protection_policy` (`STT_6.als:231-243`). Despite its name it folds over the whole program, not only the committed prefix.
  - STT_6: a set of **states**. Seed = all `Mem_s`; a load with no unresolved branch before it (and not itself one) removes its `Inmem` location (`STT_6.als:326,329-332`). The fold is pure subtraction, so its order does not matter.
  - Recon_6: the same fold, with seed `Mem_s` minus states that reach a non-speculative load address (`Recon_6.als:316-319`). The audit found that reveal clause is a no-op (MODEL_AUDIT_SPT_RECON R-2).
  - SPT_6_oneLP_v2: a set of **operands**. Seed = every operand except register inputs that no `outreg` feeds (`:375`). Propagation subtracts declassified values (non-speculative transmitters' operands, backward over `rf`), outputs of ALU ops whose inputs are all unprotected or that have no inreg, inputs whose `rf` source left the set, and an STL rule (`:379-395`). Several rules test the *current* set `o`, so **the fold order matters**.
  - Proposed STT_6_v2 / Recon_6_v2 (model-fixes, unapproved): operand-typed, seed = the `Inmem` of every speculative load, propagation = identity (`proposed/STT_6_v2.als` `[v2-2]`, wiki/state/ALLOY_MODEL_CHANGES.md).
- **Insecure condition.** A speculative transmitter operand is in the protection set, or is reachable from it over `^(rf + ddi)` (`STT_6.als:262-265`; STT lifts states to operands with `.(~opstate)`, while SPT and STT_6_v2 are operand-typed, `SPT_6_oneLP_v2.als:286-297`).

So the checker has to reproduce, exactly: the instruction kinds, `spo`, the operand slots, `opstate` identity, the `rf` and `ddi` edges, the `committed`/`resolved`/`xm` flags, and those clauses evaluated at `no_p`.

### 1.2 What the checker must keep, and what is Alloy-only search machinery

| Part of the `.als` | Checker needs it? | Why |

At `no_p`, `fix_rf_hole_p` is empty (`p[RI]` is empty, `STT_6.als:218`), so `rf_p = rf` and `ddi_p = ddi`. |

### 1.3 Perturbations define necessity, not leak-ness

`gen_useful_litmus` (`STT_6.als:301-311`) asks for three things: the program leaks (`not secure[no_p]`); resolving any unresolved non-boundary instruction makes it secure (`RR->i`); and removing any state makes it secure (`RS->s`). Only the first clause is the leak condition. The others say each Alloy element is *needed* for the leak, which keeps Alloy from emitting redundant tests. A post-hoc checker answers "does this program still have the Alloy leak at the designated transmitter", so it evaluates `no_p` only.

Two cautions:

- **Necessity is legitimately lost by design.** A filler or splice is not necessary for the leak, and that is the point of fanout. So "the inserted program is no longer minimal" is expected, and it is not a failure.
- **Necessity of the original Alloy elements can still matter.** If an insertion made an Alloy branch's resolution unnecessary (for example, an inserted path that leaks regardless of that branch), the hit no longer means what the Alloy instance said: the window would come from somewhere else. The checker can test this cheaply under option (c), because each `RR->i` is just one more `eval` of `secure_speculation_scheme_p[RR->i]` on the same instance. This is optional and is decision D3. Note that on a graph with inserted instructions the perturbed functions apply to inserted instructions too (`RS->s` removes every operand of that state, inserted ones included), so it would have to be restricted to the Alloy atoms.

## 2. Building the execution graph from a concrete program

### 2.1 Inputs and what each gives

- **`<mode>/asm/<stem>.s` or the linked binary.** The real instruction stream. `compile_annotate.py` already resolves the `__litmus_<stem>_pcN` markers to addresses with `nm` on the linked binary (`compile_annotate.py:137-163`, so linker relaxation is accounted for) and disassembles the function with `llvm-objdump-15` (`:166-203`).
- **`<mode>/ann/<stem>.ann.json`.** Branch annotations with `mode` (`mispredict_*` = unresolved, `correctly_not_taken` = resolved) and the BTB-forced target address; `xmit` (pc, kind, atom); `commit_boundary.first_noncommitted`; `reg_naming` (locked Alloy registers and infra registers); and the insertion records `fanout_v2` (splices, fillers, `otb`), `fpr` (xmm routes) and STL retargets (`parsexml.py:pass5_emit_llvm`; schema in wiki/design/CONCRETIZATION_PASSES.md §4).
- **`<mode>/llvm/<stem>.ll`.** Each Alloy instruction carries a comment `pc=N <atom> (<concrete>)` (`parsexml.py:2603`), which gives the pc → Alloy atom → concrete op map without re-running pass 1.
- **`xml/<stem>.xml`.** The original instance: its flags (`isresolved`, `iscommitted`, `isxm`) and its `rf`/`ddi`, which the checker compares against (step 6 below).

### 2.2 Algorithm

1. **Trace = the speculative path, not the layout.** Start at the function entry and walk the instructions. At each Alloy branch, continue at the annotation's `btb_forced_target_addr`; elsewhere follow unconditional jumps; stop after the last Alloy pc's block. The layout really does differ: in `testsets/STT_6_a3c_draft/mispredict_not_taken/asm/inst-000001.s`, LLVM inverted the pc0 branch (`je .LBB0_1` jumps *into* the Alloy body and `end_block` is the layout fall-through), so a layout-order walk would leave the Alloy region at the first instruction.
2. **Classify each x86 instruction into micro-op nodes** of the Alloy kinds (table in 2.3), with explicit read and write sets.
3. **States.** Each architectural register is one `Reg_s` (sub-registers alias it), plus one `Reg_s` for the flags (see 2.4). Each distinct memory location is one `Mem_s`. Alloca slots are named by their constant `rsp` offset, since `rsp` is fixed in the body after the prologue pushes. A `probe_mem` access whose index is a data register has a data-dependent address, so it gets a fresh `Mem_s` that aliases no Alloy slot, which is true by construction (pass 3 keeps chains and probes off Alloy memory, MODEL_AUDIT Q3 rules 1-2).
4. **`rf` = most recent writer**, over registers and memory along the trace. This satisfies `rf_from_most_recent_writer` by construction, which Alloy instances only satisfy because of the fact. A read with no earlier writer has no `rf` (initial value).
5. **`ddi` = the full intra-instruction dataflow** of each node: ld `Inmem→Outreg`, st `Inreg→Outmem`, ALU every `Inreg→Outreg` (`STT_6.als:171-174`). Unlike an Alloy instance, which may omit a ddi edge (the SPT audit's "load without `Inmem`", MODEL_AUDIT S-1/Q2c), a real instruction always has its dataflow.
6. **Flags.** `xm` = the node that plays the transmitter role at `ann.xmit.pc`. `committed` = every node before the `first_noncommitted` marker on the trace (`parsexml.py:commit_boundary`, `:1981`; inserted instructions inherit by position). `resolved` = a branch node whose annotation is `correctly_not_taken`, or an inserted branch (decision D4); for non-branches, `resolved` only feeds `no_unresolved_mem_p`, which no current contract uses (`STT_6.als:258-260`).
7. **Cross-check against the XML.** Every Alloy `rf` edge should map to a path in the concrete graph from the producer's node to the consumer's node, through nothing but inserted value-preserving nodes. This is the check `verify_fanout_v2.py` already does on the pass-4 IR (`STAGE2_compilation/proposed/verify_fanout_v2.py:51-58`, via `measure_xmit_path_alu.all_edges_intact`). Any Alloy edge that is missing, or any new edge into an Alloy operand, is reported. That catches the stale-rf class (MODEL_AUDIT R-3: 50/3,000 Recon programs read a constant-derived value) before any gem5 time is spent.
8. **Evaluate** (section 3) and report: is the designated transmitter flagged; which other transmitters are flagged (new speculative transmitters created by an insertion); which well-formedness facts fail; which vocabulary bounds are exceeded.

| `cqto`, `idivq`, `imulq` one-operand, `setcc`, 8/16-bit writes | implicit reads and writes | `cqto` reads rax and writes rdx, `idivq` reads `rdx:rax`; partial-register writes merge (they read the old register). The rmw corpus skips `idivq`/`cqto` for exactly this reason. |
| `mfence`/`lfence`, `push`/`pop`, `jmp`, `ret` | no node / st or ld to the stack + rsp ALU / none | `lfence` inside the window would end speculation in hardware, but the model has no fence kind, so the builder must flag it (generator rule: none in the window). |

The read/write sets have to be the **gem5 micro-op** ones, not the ISA manual's, because the defenses track taint per micro-op (the `mov2int` case is the proof). One table per gem5 ISA tree is enough: STT, Recon and SPT are all X86 builds.

### 2.4 Known x86 traps, and how the builder handles each

- **SIB / `lea` (OTB_GENERATION_GAP.md "analysis pitfalls"; CLAUDE.md chain-interleaving note).** A naive operand parser counts the base register of `(%base,%idx,1)` as data, or misses that `leaq 0($0),$0` (splice `lea0`) is a register-to-register op. Use a real disassembler (`llvm-objdump`, as `compile_annotate.py` does) and decode address operands structurally.
- **`mov2int` reads its destination.** Covered in the table. This is why the fpr route zeroes `%out` first. A checker that misses it would report a value path that gem5 does not have (or the reverse).
- **Flags are a dataflow edge.** `testq`+`jcc` carry the branch predicate through RFLAGS. Every flag-writing instruction (most ALU ops, including fillers and splices, which declare `~{flags}`) is a most-recent-writer candidate. If an inserted ALU op ever landed between a `test` and its `jcc`, the branch would read the wrong predicate. Today pass 5 emits test+jcc from LLVM `icmp`/`br` after the Alloy asm block, so it cannot happen, but the checker would catch it.
- **Micro-op splits.** RMW, `movq %gpr,%xmm`, push/pop, `idivq`. Kinds attach to micro-ops, and the transmitter role attaches to the specific micro-op (the load micro-op of an RMW). The pc marker marks the first byte of the macro-instruction (`parsexml.py` pass 5, `mkr`, `:2609`).
- **One Alloy instruction becomes several x86 instructions.** A br_x is `movq`+`testq`+`jcc`; an fpr-routed load is four instructions in one asm block. The marker identifies only the first. The role carrier is "first instruction" for ld/st/ALU and "first `jcc` at or after the marker" for branches (`compile_annotate.py:find_branch_at_pc`, `:206-220`). Everything else in the block is glue, a node the XML does not have. An explicit role record from pass 5 would remove this guesswork (decision D5).
- **The prologue and infra.** Before the first Alloy pc, the function zeroes `eax` and copies it into every locked register (`asm_force`, `parsexml.py` pass 5) and initialises stack slots. These are real instructions that gem5 executes. With them in the graph, every "unfed" Alloy input becomes `rf`-fed by an init copy, which changes SPT's seed (`o_p - ((Inreg+Inaddr) - outreg.rf)`, `SPT_6_oneLP_v2.als:375`) and is then undone step by step by the forward-untaint rules. Whether that is faithful depends on the fold covering every instruction, which is why the depth trap below matters. Including or excluding infra is decision D6.
- **Fold depth.** `last_committed_protset_p` applies `a[...]` at `f.spo^0 … f.spo^6`, 7 positions (`STT_6.als:232-243`). Instructions past position 7 are silently skipped. With a prologue, glue and insertions, real programs have 15-30 nodes. For STT_6 a skipped instruction can only make the set larger, and a skipped late instruction is behind the unresolved branch anyway, so it cannot declassify. For SPT, skipped steps keep values protected, so the result over-flags. The harness must cover the full program length: textual unrolling for STT/Recon, an iterative fold for SPT (prototype below).

### 2.5 Two routes to the graph

- **IR replay (cheap, already prototyped).** Re-run passes 1-4 deterministically from the stem seeds, then apply the recorded `fanout_v2`/`fpr`/`otb` insertions as dataflow ops, as `verify_fanout_v2.py:26-34` does. This is exact with respect to what parsexml *intended*, but blind to what LLVM and the assembler did: register coalescing, spills, a compiler `leaq` on a locked register (the reason infra registers exist, `parsexml.py` pass 5 "Reserved virtual-pool registers"), or scheduling.
- **Assembly (herd-like, on the real artifact).** Walk the linked binary's disassembly as in 2.2. This sees exactly what gem5 runs, at the cost of an x86 semantics table and the role mapping.

**Recommendation:** the assembly route, with IR replay kept as a cross-check (the two should agree on every Alloy edge; a disagreement is either a compiler artifact or a builder bug).

## 3. Keeping it faithful to the `.als`

| | (a) Hand-port to Python, cross-checked against Alloy | (b) Generate Python from the `.als` defense block | (c) Alloy evaluates the concrete graph |
|---|---|---|---|
| How | Re-implement each defense in Python. `mf_semantics.py` already does this for `stt_old`, `recon_old`, `stt_v2`, `recon_v2` (`STAGE3_gem5/triage/model_audit_20261108/mf_semantics.py:96-114`), including the necessity clauses (`:136-150`). | A small relational interpreter (join, `~`, `^`, `*`, `+ - &`, `<: :>`, function calls) that parses the defense block and the skeleton functions from the `.als` text. | Write the graph as an instance XML, load it with `A4SolutionReader.read` against the model's sigs, and `eval` the model's own expressions (prototype `PosthocEval.java`). The SAT form (a fully pinned predicate plus `run`, like `stage_seed.py`) also works but needs a SAT call and a scratch model per program, so it is strictly worse. |
| Faithfulness | Only as good as the port. Easy-to-miss relational details: `inreg.o` means "instructions with *some* inreg in `o`" (`SPT_6_oneLP_v2.als:388`); `.*(~rf_p)` is reflexive (`:384`); STT's state→operand lift (`:263`); and the fold depth. Needs a standing differential against Alloy on every model change. | Faithful for the subset it parses. Fails loudly on new syntax. | **By construction** for every `fun`/`pred` body. The two harness-level pieces (unrolled fold, fact classification) are cross-checked against the model's own predicate wherever the program has ≤7 nodes. |
| Cost per program | ~0.1 ms (measured, below) | ~0.1-1 ms | 4-26 ms (STT family, measured); SPT needs the iterative fold |
| Maintenance per model change | Manual re-port + re-validate (every `.als` edit, v2-n proposal, new defense) | Only when new syntax appears | **None** for defense-block edits. A skeleton edit that renames a function or changes the fold shape needs the harness's two skeleton pieces updated. |
| Main risks | Silent drift, which is the exact failure the "single source of truth" rule exists to prevent | Building and maintaining a partial Alloy interpreter | JVM dependency (Java 17 is already required), the fold unroll and fact classification living outside the `.als`, and Alloy's bitwidth (4 in today's instances, so `#` counts above 7 wrap; only the vocabulary-bound facts use `#`, and those are not evaluated) |

**Recommendation: (c) for the source of truth, (a) as a fast pre-filter and differential.** Under (c) the `.als` is still the only definition of what a leak is. Keep `mf_semantics.py`-style ports for interactive triage and for million-program sweeps, and run them against (c) on a sample whenever a model changes; a disagreement means the port is stale. (b) is not worth building while (c) works.

## 4. Prototype and measurements

Run on the Mac 2026-11-08 22:05-22:15, one Java process, after the model-fixes queries freed the slot. Inputs: the 3,000-instance `STT_6` sample `results/model_fixes_20261108/sample_STT_6.out/` and the `SPT_6_oneLP_v2` sample `results/spt_v2_20261108/xml_v2/`. These are *graph-level* stand-ins for Stage-2 insertions built by `graph_xml.py`, not compiled programs: `splice` (a value-preserving ALU on the transmitter's rf edge), `filler` (reads the transmitter's source and writes a fresh register), `reload` (a committed load of the speculative load's location placed first; Stage 2 never does this, it is the negative control), and `splice2_reload` (two splices plus reload, 9 instructions, which exercises the fold depth). The asm graph builder (section 2) was not prototyped.

|---|---|---|

**What the SPT numbers mean.** SPT's propagation mentions the incoming set `o` several times (`SPT_6_oneLP_v2.als:381-392`). Nesting `a[...]` N deep therefore builds an expression tree that grows roughly like (uses of `o`)^N, and Alloy's evaluator translates the tree before evaluating it. STT's fold mentions `s` once, so it stays linear. Textual unrolling is fine for STT/Recon/STT_v2 but not for SPT. The fix is to do the fold **iteratively in the harness**: evaluate one `prot_set_propagation_p[no_p, <instr>, <set>]` step, then feed the resulting atom set back in as a literal for the next step. That still uses the model's own function, at N small evaluations per program. Alloy's GUI evaluator accepts atom names in expressions, which suggests the API allows atom literals (from memory, unverified). This is the first thing to prototype if the checker is built.

**Cost in context.** At about 25 ms per program, a 100k-program fanout testset is about 40 min on one core, and the work parallelises per batch. That is small next to gem5, which spends seconds to minutes per test. The hand-port is about 200× faster, which is why it is useful as a pre-filter.

## 5. Where it plugs in

- **Post-Stage-2 validator for the fanout options (first use).** Run on every `fanout_v2`/`fpr`/`otb`/store-separation testset, as a gate between `asm` and `gem5` (same position as `verify_fanout_v2.py`, which it generalises). Output: one JSON row per test (`xm_flagged`, other flagged transmitters, broken Alloy edges, failed well-formedness facts, exceeded vocabulary bounds). Programs whose designated transmitter is no longer flagged are dropped or bucketed before gem5, so no hit is ever scored on a program that no longer has the Alloy leak. It also replaces hand reasoning such as the 13 generator rules in MODEL_AUDIT Q3: instead of proving each insertion kind safe in advance, check each program.
- **A diagnostic `disqualifier`.** A `diag_posthoc_noleak.py` in a results folder's `diagnostics/` (phase `disqualifier`, `NEEDS_GEM5=False`) that buckets hits whose program fails the check. It is conservative by construction: it only buckets when Alloy says the designated transmitter is not flagged.
- **Fallback for Stage 1.5 at bigger bounds.** If the stage15-bound study (wiki/design/TWO_PHASE_MODELS.md) finds that a looser skeleton with more instructions does not scale in Alloy, Anna's fallback is looser randomization plus post-hoc checking (claudelog 2026-11-08 ~21:15). This checker is that post-hoc step: generate candidate programs (random flesh around an Alloy core, or random programs), then keep the ones where the leak condition holds. Evaluation is linear in program size and has no search, so the bound is set by the generator, not by Alloy. What it cannot give is minimality (1.3) or the guarantee that *every* shape up to a bound was produced. Coverage then becomes a sampling claim, which matters for how the paper states completeness (decision D7).
- **Not a replacement for gem5.** It decides the *Alloy* condition. Whether gem5 lets the leak happen is still the research signal.

## 6. Recommended design (summary)

`posthoc_check.py <testset> <mode> --model <als>`: (1) for each stem, build the micro-op graph from the linked binary plus `.ann.json` (assembly route, x86 micro-op table, speculative-path trace, most-recent-writer `rf`, full `ddi`); (2) cross-check the Alloy edges against the XML (IR replay as a second opinion); (3) emit an instance XML per program; (4) one JVM per batch runs `PosthocEval` with the model's `secure_speculation_scheme_p[no_p]` (for ≤7 nodes) and the harness-unrolled fold (for any size), plus the well-formedness facts; (5) write `posthoc.json` next to the testset and gate the gem5 phase on it. The `.als` is read, never edited. The harness owns exactly two skeleton-level pieces (the unrolled fold expression and the fact classification), both checked against the model on small programs.

## 7. Decisions for Anna

- [ ] **D1: two-register addresses.** Alloy has one `inaddr` and no address→value edge. Options: (a) a virtual `agen` ALU node (base, index → address) feeding one `inaddr`; (b) several `inaddr` operands on one load (breaks `limited_inaddrs` and typing in SPT's backward declassification); (c) drop the infra base register. Implication: identical for STT/Recon (any protected input reaches the transmitter), different for SPT (declassifying the address untaints the `agen` output only under (a), both registers under (b)). gem5-spt does no backward untaint through `lea` (MODEL_AUDIT S-5). **Recommendation: (a).**
- [ ] **D2: flags.** Options: (a) one `Reg_s` for RFLAGS, and `test`/`cmp` as an ALU writing it; ALU ops that write a register *and* flags become two nodes; (b) ignore flags and give each `jcc` the register its `test` read. (b) is simpler but misses a clobber between the test and the jcc. **Recommendation: (a).**
- [ ] **D3: also check necessity of the Alloy elements?** Options: leak-ness only, or also re-evaluate `RR->i` / boundary `RC+RR` / `RS->s` restricted to the Alloy atoms. Leak-ness alone answers "does the test still mean an Alloy leak". Necessity answers "does the hit still mean *this* branch's window". **Recommendation:** leak-ness as the gate, necessity as a reported flag.
- [ ] **D4: inserted branches.** The contract only knows Alloy branches. Options: inserted branches are resolved (as gem5 sees a correctly predicted branch) or forbidden before the transmitter (MODEL_AUDIT Q3 rule 3). **Recommendation:** forbid in the generator, and report as a builder error if seen.
- [ ] **D5: ask pass 5 to emit a role record** (per Alloy pc: which byte offset carries the ld/st/br role, which instructions are glue) into `.ann.json`. It is additive and a `parsexml.py` change, so it needs your approval. It removes the "first `jcc` after the marker" heuristic. **Recommendation: yes,** when the checker is built.
- [ ] **D6: include the prologue/infra in the checked trace?** (a) Yes, the whole trace from function entry, which is what gem5 runs; changes SPT's seed via the init copies and relies on the unrolled fold. (b) Only the Alloy region plus insertions, treating infra writes as "initial values". (a) is more faithful to the program, while (b) matches the instance's meaning of "unfed". **Recommendation: (a),** reporting the answer under (b) too until the two have been compared on a corpus. A difference would itself be a finding about the SPT seed.
- [ ] **D7: if Stage 1.5 falls back to random generation plus this checker, how is coverage claimed?** Alloy gives exhaustive-up-to-bound; sampling plus the checker gives "every reported test provably has the leak" but not completeness. This is a framing decision for the paper.
- [ ] **D8: build it now or keep it as a design?** The fanout work (OTB merges, new vocabulary) is adding insertion kinds quickly, and each currently relies on hand-argued rules. **Recommendation:** build the assembly-route graph builder plus `PosthocEval` as the post-Stage-2 gate for the fanout testsets first.
