# Branch resolution hooks, the derived branch force, and the hook audit (2026-10-30)

Design reference for how SimSpect makes gem5 run the speculation shape an Alloy instance asks for, and how it measures branch resolution. Built and verified 2026-10-30 with Anna's OK ("you can back up and modify and build"). The evidence and the impact on earlier campaigns are in [`wiki/findings/bug/BRANCH_ANNOTATION_AND_FORCE.md`](../findings/bug/BRANCH_ANNOTATION_AND_FORCE.md). The earlier read-only survey that this builds on is [`RESOLUTION_HOOKS_SURVEY.md`](RESOLUTION_HOOKS_SURVEY.md). The lc/fnc rules are in [`COMMIT_BOUNDARY.md`](COMMIT_BOUNDARY.md).

## 1. What the gem5 builds now print and do

All 8 hooked builds carry the same three edits: stt, stt-dbg, gem5-spt, gem5-recon-modded, and amulet InvisiSpec, CleanupSpec, SpecLFB and STT. The generator is `gem5-hooks/resolve/apply_resolve_hooks.py` and the applied diffs are `gem5-hooks/<build>/resolve_hooks.diff`. gem5-recon (the unhooked control) and sdo were not touched. Lines use the `O3PipeView:simspect:` format of [`SIMSPECT_HOOKS.md`](SIMSPECT_HOOKS.md) with `struct=BR`, print under the existing `O3PipeView` flag, and parse with `gem5_common.parse_branch_events`.

| line | where | meaning | extra fields |
|---|---|---|---|
| `predict_force` | `bpred_unit.cc`, in the existing `btbForcedTargets` override | fetch applied an annotated forced prediction to this dynamic branch | `taken` (0/1), `target` |
| `resolve_hold` | IEW resolve-stall hook, when the deferred event is scheduled | the branch executed and its resolution is being held | `stall` (cycles), `fire` (tick the release is scheduled for), `mispred` |
| `resolve_drop` | inside the deferred event, on the `isSquashed()` early return | the branch was squashed before release: it never resolves | |
| `resolve_release` | inside the deferred event, after `setExecuted(); instToCommit()` | IEW releases the branch | `mispred` |
| `resolve_bcast` | inside the deferred event, after `squashDueToBranch` | the release broadcast the mispredict squash | |
| `resolve_visible` | commit `markCompletedInsts`, right after `setCanCommit()`, for every control instruction | the tick every defense treats as "resolved" (`readyToCommit`, then `updateVisibleState` / taint / shadow free in the same tick; see survey §B) | `upc`, `mispred`, `stall` (registered for this PC, 0 if none) |

**Behaviour changes, two:** edit 4 below (the release wakes the CPU), and a forced target of `1` now means "force predict NOT-TAKEN". Any other value still forces taken to that address, as before. Address 1 is never a real PC, and no annotation before 2026-10-30 used it. Everything else is print-only. Verified: the non-simspect pipeview, commit squash ticks and ready-in-ROB ticks of 546 / 546 audit runs are identical between the pre- and post-rebuild binaries (§4).

**Gating tick: `visible`.** The window "branches still unresolved" ends at `resolve_visible` (falls back to `resolve_release` if a branch released but never became visible). The IEW release is exactly `hold + stall` cycles (audit `br_hold_release`, all 8 builds), and since the wake fix (edit 4 below) commit marks the branch ready exactly `iewToCommitDelay` = 1 cycle later in every audited instance (223 / 223 release→visible pairs, 7 builds; gem5-spt audit in `post_wake_spt.json`). Before the wake fix, 28 of 331 pairs lagged 27–40 cycles and 4 never became visible. That was not a defense effect: the CPU had gone idle while the branch was held, so the release sat in the IEW→commit buffer until something else woke the CPU, or forever (`wiki/findings/audits/2026-10-30/RESOLVE_HOOKS_CODE_AUDIT.md`, which also corrected my first reading of it as STT's pending-squash path). Gating on `visible` is still the right choice: it is the tick the defense acts on, whatever delays it.

**Edit 4: the release wakes the CPU (behaviour fix, 2026-10-30).** Present in all 8 builds since the 21:27–21:42 rebuild (`apply_resolve_hooks.py:patch_iew_wake`). The deferred release now calls `wakeCPU()` before `setExecuted(); instToCommit()` and `activityThisCycle()` after, the same pattern as gem5's own late memory response. Without it a branch held long enough for the ROB to fill and the CPU to sleep was never released: gem5 ran to `--abs-max-tick` (1e11) with the program frozen (stt, inst-000733 mispredict_taken, 1213 CPU cycles simulated). Every campaign that used the 5000-cycle unresolved stall had such frozen runs. The validity gate now flags them (`window_opened` False). `wakeCPU()` is a no-op while the CPU is running: 524 of 536 audit traces are identical before and after; the 12 that changed are exactly the frozen/late-wake runs. The print-only binaries are kept as `build/<ISA>/gem5.opt.resolve-print-only-20261030`.

**Ticks we have per branch** (all in each record's `br_events`): `predict_force` (fetch), `resolve_hold` (execute; equals pipeview `complete`), `resolve_hold_fire` (scheduled release), `resolve_release` (IEW), `resolve_bcast` (squash broadcast), `resolve_visible` (commit: what the defense sees), plus the Commit-flag `Squashing due to branch mispred` tick (fetch redirect; `parse_commit_squashes`). STT/SPT's implicit-channel "made pending" squash is still read from the Commit text (survey §B step 4), not a BR line.

## 2. The derived branch force (rule)

**Rule.** For every annotated branch the harness forces the x86 direction whose straight-line path reaches the next Alloy instruction's label (`__litmus_<stem>_pc<N+1>`). For an unresolved or xmit branch that path is the speculative critical section. For a resolved branch it is the architectural path. The force is "not-taken" (target 1) when the fall-through reaches it, or "taken to the jcc's own static target" when the taken side does. It is never forced to the label address.

**Where.** `STAGE3_gem5/gem5_common.py:branch_force_plan` (objdump + nm of the linked test binary), applied in `_branch_ann_for_se`, the one place an annotation is handed to gem5. It is applied only when the gem5 binary has the resolve hooks (`binary_has_resolve_hooks` finds the `BR:predict_force` format string in the binary). On an older binary the annotation is passed through as before, plus the key alias. The plan is written to `force_plan.json` in the test workdir and copied into every result record (`force_plan`). Entries get `mode: "simspect_force"` so every se.py loader passes the target through (they zero the target for `*_not_taken` modes). `orig_mode` keeps the model's mode.

**Why (each measured 2026-10-30, details in the findings doc).** (a) In mispredict_taken mode LLVM puts the critical section on the x86 fall-through and makes the architectural bypass the jcc's taken edge. The old rule forced "taken to the pc+1 label", which can sit past LLVM-hoisted instructions (e.g. a `lea` that sets the base register). Old-gem5 builds then fetched the wrong path mid-block. On gem5-22 builds (recon-modded, SpecLFB) decode saw a predicted-taken direct branch with a target different from its static target and squashed it at decode, so the branch never mispredicted at execute, the resolve stall never ran, and there was no window. (b) Not-taken modes and resolved branches relied on the cold predictor's not-taken guess. When the layout puts the next Alloy instruction on the taken side, an unresolved branch was predicted correctly (no window) or a resolved branch mispredicted (an extra window the model doesn't have).

**Reachability** follows direct unconditional `jmp`s (up to 4 hops), so the LLVM layout `jcc X; jmp bb_next` is handled. **Degenerate case:** a jcc whose static target equals its fall-through cannot mispredict; it is forced not-taken. **Flags-idiom fallback:** when no next-Alloy label is reachable (the last Alloy branch), the direction comes from the codegen's constant flags (`xor %r,%r; test %r,%r` sets ZF=1: `je` taken, `jne` not taken), architectural for `correctly_not_taken`, the opposite for a mispredict mode. **Cross-check:** whenever the idiom is present the plan records `consistent_with_arch`, and a contradiction makes `force_applied` False (record invalid). Census 2026-10-30 (1,500 tests per testset and mode, STT_6 / STT_6_interleave / SPT_6_oneLP / Recon_6 / STT_all / STT_6_commitsplit; cafe2 `/tests/claude_hookaudit_20261030/plan_census2.json`): no branch left `unknown`, and no contradiction once the check follows the annotated mode. A branch that still ends up `unknown` gets no force at all, never the old label rule.

## 3. What the checkers enforce now

Per record (all checkers through `gem5_common.process_one`):

- **Window = model-unresolved branches still unresolved.** `collect_unresolved_branches` takes only non-`correctly_not_taken` entries with a stall. Before 2026-10-30 a resolved branch carrying a sweep grid stall was also required to be unresolved at the signal, the opposite of the model. `check_branch_resolutions` uses the observed `resolve_tick` (= visible) when the binary prints BR lines (`branch_resolutions[*].source = "observed"`), else the old estimate (`"estimate"`).
- **Execution validity** (`gem5_common.execution_validity`, in `record.validity` and in `criteria`): `resolved_correct` (no resolved branch mispredicted on a retired instance), `window_opened` (the oldest non-xmit unresolved branch mispredicted on its retired instance), `stall_applied` (every resolved instance of a stalled unresolved branch has a `resolve_hold`), `force_applied` (every planned branch's visible instance had a `predict_force`). Any False sets `issued_in_window=False` and `status="invalid"` (counted as `sweep_invalid` in the sweep aggregate, not as an error), stores the checker's verdict in `issued_in_window_unvalidated`, and gives the reason in `error`. None means "does not apply" or "binary has no BR lines".
- **Resolved branches, reported not gated:** `record.resolved_before_signal` (deliberately outside `criteria`, whose non-None values AND to `issued_in_window`) and `record.resolved_branches[*].visible_tick`. The model says a resolved branch has resolved at the leak. Whether to gate on this is Anna's call. It is recorded so the data can answer whether it ever matters.
- **lc strict** in check_ld, check_br and now check_other (`lc_retired` criterion: a specified lc that never retires disqualifies).
- **fnc commit stall off** in the fixed configs (`runconfigs/fixed_20261030/`). `before_fnc` is enforced against fnc's real retire tick.
- **Every criterion is saved** (`criteria` dict in check_ld, check_br, check_other, plus the validity keys), along with `br_events`, `force_plan` and `branch_resolutions`. The sweep path saves full per-record checker output under `<mode>/_sweep_raw/` (testrun) or `sweep/raw_results/` (pipeline), so any criterion can be re-analyzed without re-running gem5. Raw file names carry a per-invocation timestamp, so a resumed run never overwrites earlier raw outputs (before 2026-10-30 the pipeline streaming path restarted its counter and overwrote them).

## 4. The hook audit (how to check the hooks do what they claim)

`STAGE3_gem5/hook_audit.py` runs each test several times on one binary, switching one hook at a time, and compares pipeline traces:

```bash
# inside the gem5_dev container, from a checkout that has STAGE3_gem5/
python3 STAGE3_gem5/hook_audit.py --build all --testset /tests/simspect/testsets/STT_6 \
    --n 6 --jobs 32 --keep --out hook_audit.json
```

Variants: `none` (no hooks), `raw_S` (the .ann.json exactly as compile_annotate writes it, unresolved stall S), `ann_0` / `ann_S` / `ann_R` (key-aliased old-style annotation: no stall / unresolved stall / resolved stall), `fnc_F` (fnc commit stall only), and on hooked binaries `plan_0` / `plan_S` (exactly the production hand-off: alias + derived force). Checks: registration in `config.ini`, raw == aliased trace, force effect, resolved branches never mispredict, stall shifts the squash and ready-in-ROB tick by S, resolved stall shifts by S, fnc stall shifts fnc retire by ≥ F, BR hold/release/visible consistency with the Commit trace, plan completeness, and plan_0 / plan_S execution validity and stall shift. Each variant also stores a fingerprint (`sha`) of its non-simspect pipeview + squash + ready ticks, so a rebuild that should be print-only can be proven print-only by comparing two audit JSONs.

Results 2026-10-30 (STT_6, 6 tests per mode, 8 builds): `wiki/findings/audits/2026-10-30/hook_audit_pre_rebuild_sha.json` and `hook_audit_post_rebuild_all.json` (variant detail stripped; full JSONs with workdirs in cafe2 `/tests/claude_hookaudit_20261030/`). Summary in the findings doc.

## 5. Rebuild, backups, rollback

- Rebuild one build: `gem5-hooks/resolve/rebuild_resolve_hooks.sh <build>` (in the container). It copies the binary to `build/<ISA>/gem5.opt.pre-resolve-hooks-20261030`, tars the three original source files to `/work/simspect_backups/resolve-hooks-20261030/<build>-src.tgz`, applies the patch (idempotent: it skips files that carry the marker), runs scons -j6, and logs to `/work/simspect_backups/resolve-hooks-20261030/<build>.log`.
- Roll back one build: `cp -p build/<ISA>/gem5.opt.pre-resolve-hooks-20261030 build/<ISA>/gem5.opt`, and for the source `tar xzf /work/simspect_backups/resolve-hooks-20261030/<build>-src.tgz -C <root>`.
- All 8 rebuilt 2026-10-30 19:33–19:35 UTC (edits 1-3) and again 21:27–21:42 (edit 4), rc=0. sha256 of each binary is in the per-build log. Binaries: `.pre-resolve-hooks-20261030` (before any of this), `.resolve-print-only-20261030` (edits 1-3), `gem5.opt` (edits 1-4).
