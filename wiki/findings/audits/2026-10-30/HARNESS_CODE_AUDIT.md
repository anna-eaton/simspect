# Harness code audit, 2026-10-30 (resolve hooks, force plan, validity gate)

Adversarial read-only review of the uncommitted STAGE3 changes (`STAGE3_gem5/gem5_common.py`, `check_br.py`, `check_other.py`, `hook_audit.py`), the committed 2026-10-29/30 changes in `check_ld.py`, `pipeline.py`, `STAGE2_compilation/{parsexml.py, compile_annotate.py, batch_generate.py, audit_commit_boundary.py}`, and the working-tree STL alias-load change in `parsexml.py`. I re-read the current files after the coordinator's two later edits: the degenerate `static target == fall-through` case in `branch_force_plan` and `hook_audit`'s `plan_stall_shift`, which now requires release minus hold == S. I checked gem5 sources on cafe2 (`gem5_dev`): every se.py loader, plus `/work/stt` `iew_impl.hh`, `commit_impl.hh` and `bpred_unit.cc`. Severity: **BUG** = gives a wrong answer or loses data today. **RISK** = gives a wrong answer for a reachable input, or is fragile. **NIT** = cosmetic or a weak edge case.

## Verified correct (no finding)

- **se.py loaders pass target 1 through.** `/work/stt`, `/work/stt-dbg`, `/work/gem5-spt` and all four amulet `configs/example/se.py` set `tgt = 0` only for `mode in ('correctly_not_taken','mispredict_not_taken')`. The mode `simspect_force` takes the `else` branch, reads `btb_forced_target_addr_hex` first (`int("0x1",0) == 1`), then the non-hex key. `/work/gem5-recon-modded` uses `_ann_to_addr`, which also takes the first key present, `_hex` first and absolute. `_branch_ann_for_se` (gem5_common.py:270-312) writes both keys with the same value and pops the relative `*_x86_offset*` keys, so `_hex` precedence cannot pick a stale value. `bpred_unit.cc:84` drops `tgt == 0`, and the hook treats `== 1` as forced not-taken (advancePC; predTaken=false).
- **Hook detection works on every hooked build.** `binary_has_resolve_hooks` looks for `BR:predict_force`. That string appears verbatim in the DPRINTFR format string, and `grep -c -a -F` finds it once in each of stt, stt-dbg, gem5-spt, gem5-recon-modded and all four amulet gem5.opt builds.
- **The hold covers every executed instance.** In IEW (`/work/stt/src/cpu/o3/iew_impl.hh` ~1336) the stall is looked up for every `isControl()` instruction at that PC, whatever its prediction. Wrong-path instances that execute are held too. `stall_applied`'s rule "resolved without resolve_hold ⇒ stall not registered" is therefore sound.
- **resolve_visible marks the defense-visible tick.** Commit prints it for non-squashed control micro-ops inside `markCompletedInsts`, at the `setCanCommit()` point. Its `seq` and `pc` match the pipeview `fetch` seqNum and `instAddr`, so the joins against `parse_pipeview_by_seq` are correct.
- **The parser handles the string fields.** `parse_simspect_line` returns strings for unknown keys (`mispred`, `stall`, `fire`, `taken`, `target`, `upc`). `parse_branch_events` (gem5_common.py:852) converts them with `int(v, 0)` and skips `None` ("-"). `%d`/`%llu`/`%#llx` never print leading zeros, so base-0 parsing cannot raise.
- **Checker criteria still AND to `issued_in_window` at the checker level.** check_ld: `issued = data_obtained if gated else in_window`, and `criteria.data_obtained` is non-None exactly when the gate applies. check_br: the five other criteria plus `branch_redirected`. check_other: the new `lc_retired` disqualifier enters both `issued_in_window` and `criteria`. The invariant breaks later, in `process_one` (finding 1).
- **Pipeline seeds are now stable.** `zlib.crc32` replaces the salted `hash()` in `pipeline.py:457,916` and `batch_generate.py:101`, so grid sub-samples and variant seeds reproduce across processes.
- **`commit_boundary` (parsexml.py:1902) is correct for the cases it targets.** It skips `synthetic` records (chain steps, the xm NOP), so neither lc nor fnc can be a chain step. For older models `must_uncommitted` defaults to `not committed`, which reproduces the pre-fix fnc whenever the first uncommitted record is an Alloy instruction. pass5 and the annotation both call it, so the label and the annotation agree.

## Findings

- **[BUG] gem5_common.py:1113: `criteria.resolved_before_signal` sits inside `criteria` but does not gate, which breaks `issued_in_window == AND(non-None criteria)`.** check_ld.py:150 documents that invariant, and the near-miss analysis ("exactly one criterion failed") depends on it. Failing input: a check_ld hit with a `correctly_not_taken` branch younger than the mispredicting branch (on its wrong path) and a sweep grid stall S large enough that its `resolve_visible` lands after `xmit_signal`, or that it is dropped (`visible_tick = 0` → `before_signal = False`). The record has `issued_in_window = True` and `criteria.resolved_before_signal = False`, so it is counted as a near-miss although it is a hit. Fix: move it out of `criteria`, for example to `result["resolved_before_signal"]`, or gate on it explicitly.
- **[BUG] pipeline.py:883 (streaming sweep path): `gem5_run_n = [0]` restarts at 0 on every invocation, so resuming a streaming sweep overwrites the previous run's full per-record outputs.** The outputs are `sweep/raw_results/s{n:06d}_g{idx:04d}_{script}.json`. Those raw files are the only place the full records survive on the sweep path: `validity`, `criteria`, `issued_in_window_unvalidated`, `br_events`, `force_plan`, `branch_resolutions`. `window-results.json` (pipeline.py:540-551) keeps only name/issued/status/grid size, and the `_sweep.json` sidecar keeps only stalls/issued/status. Failing input: kill a `pipeline.py all` sweep after N batches, then rerun without `--force`. Batch 1 of the resumed run writes `s000001_g0000_check_ld.py.json` over the first run's batch 1. In the same path, `manifest.json` is rewritten at pipeline.py:1035 from the in-memory `manifest = {}`, which holds only this invocation's stems, so the earlier stems' grid assignments drop out of it too (they survive only in the sidecars). Fix: seed the counter from the existing raw files (or name them by timestamp or PID), and merge into `manifest.json` rather than overwriting it.
- **[RISK] pipeline.py:535/548 and gem5_common.py:1121: a record that fails the validity gate gets `status="warn"`, so the sweep aggregate marks the whole stem `status: "error"`.** The aggregated row also keeps no trace that a hit was suppressed, because `issued_in_window_unvalidated` is not copied. Failing input: any test whose oldest unresolved branch did not mispredict on one grid point. `window-results.json` then shows `error`, the same as a crashed gem5, and `run_batch` and `_collect_batch_results` count it as an error. Suggest a separate `invalid` status, plus copying `validity` and `issued_in_window_unvalidated` into the sidecar's per-point summary and an `n_invalid` field into the aggregate.
- **[RISK] gem5_common.py:299: on a hooked build, a branch whose plan is `unknown` silently keeps its original mode.** For `mispredict_taken` that means the pre-2026-10-30 behaviour: force taken to the pc+1 label address, which the docstring says is wrong (it skips hoisted instructions, and gem5-22 corrects it at decode). Nothing gates this. `force_applied` only checks branches with a planned force, and the miss only reaches `validity.notes` ("no force plan for …"). Failing input: LLVM lays out a `mispredict_taken` branch as `jne <end>; jmp <bb_pc+1>`. The fall-through hits a `j*` and stops, the target reaches `ret`, so `_reaches` returns False on both edges and the result is `unknown`. Only `window_opened` can catch it, and only when that branch is the oldest unresolved one. Suggest marking validity False (or a dedicated `plan_complete` criterion) whenever an unresolved non-xmit branch has an `unknown` plan.
- **[RISK] gem5_common.py:205-218 `_reaches` is conservative and can make `unknown` common.** It stops at any mnemonic starting with `j`, `call` or `ret`, so an unconditional `jmp` that lands exactly on the dest label counts as "not reached". It also gives up on backward targets (`addrs[i] > dest` fails at once when dest < start) and after 64 instructions. Failing input: block placement with the speculative block placed before the branch, or the `jne X; jmp bb_{pc+1}` layout above. Both edges come back False, so the plan is `unknown` (see the previous finding). Following one unconditional `jmp` whose target is ≤ dest would cover the common LLVM layout. Labels with `-` or `.` are handled correctly: `_litmus_labels` applies the same `replace("-","_").replace(".","_")` as pass5 (`safe_name`). `--no-show-raw-insn` output matches the regex, and the `<sym+off>` target parse works because the static binary has symbols.
- **[RISK] gem5_common.py:874-886 + 889-947: dynamic-instance pairing.** `_resolution_of` takes the *youngest* live (held or visible, not dropped) instance of each unresolved branch. The checker's signal is the *latest* LSQ execute tick (check_ld.py:30-36) or `best_record` (pipeview), and nothing ties it to a particular dynamic instance. Failing input: an older event, such as a memory-order violation or an STL-hook squash, re-fetches the critical section. Branch instance A is released and then squashed (not dropped, because the release came first). Branch instance B is re-fetched and still held. If the xmit's *earlier* instance (younger than A) executed after A released, its signal is compared against B's later `resolve_visible`, so `ok` comes out True even though the branch had resolved first. The old estimate path has the same weakness. Suggest pairing each branch instance with the xmit instances that are younger than it and older than its squash.
- **[RISK] gem5_common.py:984 `window_opened` takes "oldest" to mean the lowest x86 address.** That equals program order only while LLVM keeps the Alloy blocks in pc order. Pass the Alloy `branch_pc` through and sort on that instead. Failing input: any layout that moves a later `bb_` block below an earlier one, which then gives a false `window_opened=False` (the record is invalidated).
- **[RISK] gem5_common.py:1102 `sig = xmit_signal or xmit_complete`.** check_other returns no `xmit_signal`, so it uses `xmit_complete`, which is right. For check_br, `xmit_signal` is the commit-squash redirect tick, and when the branch never redirects it falls back to `complete`. `resolved_before_signal` is then measured against a tick that is not the leak signal. It does not gate, so the harm is mislabelled reporting, which feeds finding 1.
- **[BUG, audit-only] hook_audit.py:320 → 275: `execution_validity` receives the *Alloy* xmit pc (`ann["xmit"]["pc"]`, a small integer), not the absolute address.** Its `pc != xmit_pc` filters (gem5_common.py:984, 990) therefore never exclude the xmit branch. Failing input: a br_x test whose only unresolved branch is the xmit. In process_one `nonx` would be empty and `window_opened` None. Here `nonx = [xmit_addr]`, so `window_opened` is evaluated on the transmitter itself. The xmit also counts toward `stall_applied` once the audit stalls it. Fix: pass `int(ann["xmit"]["addr"])`.
- **[NIT] hook_audit.py:286-293 `plan_stall_shift` (new rule).** `held[0]` is the first instance in trace order and may be a wrong-path or dropped-later copy rather than the retired instance. Also, `rel == S` compares floats. The comparison is exact today because IEW runs on clock edges and `clockEdge(S) = now + S·period`. A non-integer `tpc` ratio, or a build that schedules the release off-edge, would make it fail by rounding. Prefer the retired instance and compare in integer ticks: `release - hold == S * tpc`.
- **[NIT] gem5_common.py:160-170: `binary_has_resolve_hooks` reads the whole gem5.opt into memory (1.1 GB for stt and spt).** The cache is filled after the read, so with `--jobs 16` every thread that enters before the first read finishes reads it again, about 17 GB. hook_audit's ProcessPool adds about 1 GB per worker. cafe2 has 503 GB, so this is harmless today. A chunked `mmap`/`find` with a lock is cheap.
- **[NIT] gem5_common.py:867: first-wins tick, last-wins extras.** `d.setdefault(kind, tick)` keeps the first tick, while the `{kind}_{k}` extras keep the last. If a kind ever repeats for one seq, the tick and its fields would disagree. That cannot happen with today's hooks.
- **[NIT] gem5_common.py:999-1003: `force_applied` checks only that a `predict_force` line is present, not that `predict_force_taken`/`_target` match the plan's direction.** A swapped direction, for example a static target equal to 1, would pass.
- **[NIT] gem5_common.py:1121-1122: the validity override replaces `result["error"]` and sets `warn` on non-hits too.** That is noise in error counts (see the RISK above).
- **[NIT] audit_commit_boundary.py: it only flags boundaries whose atom starts with `_` (synthetic).** It cannot detect a stale *Alloy* fnc. Example: a commitsplit testset concretized before `must_uncommitted` existed, whose fnc is the first uncommitted instruction in the may-commit middle rather than the first of U. Low risk, because the commitsplit model landed in the same commit. `_ll_atoms` assumes the layout `<mode>/ann/` next to `<mode>/llvm/`, and otherwise falls back to a sibling `.ll`. That holds for testsets.
- **[NIT] parsexml.py:1243 `_stl_alias_load_matches`.** `except ValueError: continue` also swallows out-of-bounds and unknown-op errors, not only "past a taken branch". An alias load is then dropped without a log line. The store and load `space` tuples compare correctly: probe and mem are different arrays and are never treated as aliasing.
- **[NIT] gem5_common.py:233 `stem = binary.name` versus `_func_base_addr(binary, binary.stem)` in run_gem5.** For a stem containing `.` these differ (`binary.stem` drops the suffix). This is pre-existing and only affects `--branch-ann-base`. The labels use `name`, which is correct.

## Not a bug (checked)

- **Degenerate `target == fall-through`.** It is now forced `not_taken`, which is correct: either prediction is right. A trailing resolved branch is emitted with the `ftbypass` trampoline. When the trampoline's block is empty it collapses onto end_block, so the jcc's target equals its fall-through and the degenerate path is taken. Otherwise `dest` is None (there is no pc+1) and the plan is `unknown` with the original `correctly_not_taken` mode, so the predictor's default not-taken applies.
- **`collect_unresolved_branches` skipping `correctly_not_taken` (gem5_common.py:835).** This is right per the model. It changes verdicts on *all* builds, hooked or not, relative to pre-2026-10-30 runs, so old and new hit counts are not directly comparable.
- **A branch with `br_events` present but never fetched.** `_resolution_of({})` returns None, so the branch counts as "never fetched" with ok=True. This is the same as the old "not completed" rule. `window_opened` still catches the case where the oldest unresolved branch has no retired instance.
- **xmit branch forced.** It was `mispredict_not_taken` with tgt 0 (cold predictor, not-taken). It is now forced not-taken, which has the same intent and is now deterministic.
