## IS-1. Spectre mode: a trap at the ROB head hides a branch squash, so wrong-path loads become visible

- **Code:**
  - `cpu/o3/commit_impl.hh:881-883`: the IEW squash is taken only `if (fromIEW->squash[tid] && commitStatus[tid] != TrapPending && ...)`. Nothing re-sends it; the trap squash comes `trapLatency` cycles later (`:545-556`, `O3CPU.py:113` = 13).
  - `commit_impl.hh:711-713`: `commit(); markCompletedInsts();` run every tick, so the mispredicted branch still gets `setCanCommit()` (`:1418`), and `rob->updateVisibleState()` (`:1435`) runs.
  - `cpu/o3/rob_impl.hh:466-470`: a control instruction clears `prevBrsResolved` only if `!readyToCommit() || fault || isSquashed()`. A resolved but mispredicted branch passes, so younger loads get the sticky `setPrevBrsResolved()` (`:455`).
  - `cpu/o3/lsq_unit_impl.hh:1110-1131` sets `readyToExpose`, and `exposeLoads()` (`:1154`, called first in `iew_impl.hh:1196`) exposes any unsquashed load with `needPostFetch`. Loads that issue later are sent as normal reads (`lsq_unit.hh:881-901`; no `Request::SPEC`, `base_dyn_inst.hh:1075-1077`, so the DTLB fills too).
  - Outside a trap this race is closed: commit takes the squash in the same tick it marks the branch complete, and IEW applies the LSQ squash (`checkSignalsAndUpdate`, `iew_impl.hh:1588`) before `updateVisibleState`/`exposeLoads` (`:1592-1595`).
- **A realistic trap in SE mode:** a `ReExec` fault. `checkSnoop` sets it when a load has `possibleLoadViolation` (a same-address older load executed after it, `lsq_unit_impl.hh:836`) and its line is evicted from L1 (`:650-660`; evictions reach the LSQ because `send_evicts` is true for O3/x86, `configs/ruby/Ruby.py:247-255`). With a 1kB/2-way L1D, evictions are common. Validation failures also set `ReExec` (`:1840`). The faulting load at the head puts commit in `TrapPending` (`commit_impl.hh:1291,1306`).
- **Contradicts:** §IV-A1 p4 (quoted in `invisispec.json`): only the USLs "in the correct path of the branch transition to safe loads"; §V-D p6: in Spectre mode "validations and exposures are only issued for instructions in the correct path of a branch". Wrong-path loads are squashed and never re-executed, so this is a real transient footprint.
- **Litmus sketch:** (1) `P1 = mov rbx,[L]` whose address waits on a slow load, and a younger `P2 = mov rcx,[L]` that executes first, so P2 gets `possibleLoadViolation`; (2) two safe loads to L's set evict L, so P2 gets `ReExec`; (3) a branch B younger than P2, forced mispredicted, that resolves inside P2's 13-cycle trap window (the resolve-stall hook can place it); (4) a wrong-path `mov rdx,[base+secret*64]`. Expect `L1D:fill` (or `L1D:expose`) by the wrong-path seq after `BR:resolve` of B and before its `ROB:squash`.
- **SimSpect:** STT_6 does not set up the trap deliberately, so it would only hit by chance (see "Reportability"). `check_footprint` **cannot see it as written**: the Spectre window requires the annotated branches to be still unresolved, and this footprint comes after B resolves (Question 1).
- **gem5 check (2026-11-09, bug-investigate-is1): real defect by reading, not reached by our pipeline, and structurally out of reach of the E12/E12b configs.** Scratch: cafe2 `/tests/simspect_alloy_20261108/bugwork/is1/` (`trapscan.py`, `headgap.py`, logs; nothing running).
  - **No trap ever happens in our tests.** Every route into `TrapPending` prints with the `Commit` flag: a fault at commit prints `Inst [sn:N] ... has a fault` and `Committing instruction with fault` (`commit_impl.hh:1252,1293`), and both the fault route (`:1291`) and the interrupt route (`:800`) go through `generateTrapEvent`, which prints `Generating trap event` (`:547`). A `ReExec` from an eviction prints `Conflicting load` (`lsq_unit_impl.hh:651`).
  - Old corpus: all 6047 kept pipeviews of `/tests/simspect_fixed_20261030/results/STT_6_invisispec_v2hooks_{spectre,futuristic}__20261107` (recorded with `O3PipeView,LSQUnit,Squashed,ProtocolTrace,Commit`): 0 `has a fault`, 0 `Generating trap event`, 0 `Squashing from trap`, 0 `Conflicting load`. 5822/6047 have `Found possible load violation` marks (e.g. inst-049733: addr `0x7fffffffee2`, sn 620/623), so ingredient (i) is common; the L1 eviction of such a line while both loads are in flight (ii) never happens. 38 traces have `Squashing due to order violation` (store-load, an IEW squash, not a trap).
  - New two-stage campaigns: 300 re-runs of E12b `STT_6_fv2` + `STT_6_fv2fp` ld tests (75 per campaign × branch mode, seeded shuffle 1109 of each `window-results.json`), campaign config verbatim incl. per-branch stalls (via `spt_taint_probe.probe_one`, grid 0) with only `Commit,LSQUnit` added to the debug flags: 0 errors, 0 faults, 0 traps, 0 `Conflicting load`; 296/300 have possible-violation marks; 300/300 have normal mispredict squashes. The fv2 `pre_window_reads` and splices do not create the eviction.
  - **Why E12/E12b can never show IS-1 for the annotated branch, whatever the vocabulary:** the held branch is resolved `unresolved_stall` cycles (E12b: 2500/5000/10000) after its hold starts, but every older instruction commits within a few cycles of the hold, so the held branch itself is the ROB head when it resolves and nothing older can be trapping. `headgap.py` on 410 old Spectre traces (411 held branches): the gap from the last older commit to the branch's `fire` tick is ≥ 7000 ticks in all cases and ≥ 2,478,000 ticks at the 1st percentile (trapLatency 13 cycles = 6500 ticks). The one 7000-tick case (mispredict_taken/inst-018506, seq 601) is a `BR:resolve_drop`, not a resolve. Example inst-049733: hold of seq 597 starts at 3176000, last older commit sn 596 at 3180000, `fire=5676000`.
  - **What would reach it** (all three needed, matches routes 2+3 below): (i) an older load P1 whose address resolves late and a younger same-line load P2 that executes first (common already); (ii) two more fills to P2's L1D set (8 sets × 64 B = 512 B stride on the 1kB/2-way L1D) while P2 is in flight but not at the LQ head, so `checkSnoop` sets `ReExec`; note that under InvisiSpec a speculative load fills the SB, not the L1, so the evicting fills must come from committed/exposed loads or from UV1 spec evictions; (iii) a *short* or zero hold on the mispredicted branch so that it resolves within 13 cycles of P2 reaching the ROB head, i.e. route 3's dense `unresolved_points` sweep instead of the long hold. Not tried as a hand-built test: it needs address re-layout of the branch annotations plus timing tuning on a loaded node, and a hand demo would not be reportable anyway (Anna's rule above).

## IS-2. Futuristic mode: "validated" is not "unsquashable"

- **Code:** `base_dyn_inst.hh:807-818` (`isLoadSafeToCommit`) treats a load as safe once its expose is sent or its validation has completed, and `rob_impl.hh:482-487` then lets younger loads become `PrevInstsCompleted` and get exposed. But `lsq_unit_impl.hh:650-660` still sets `ReExec` on any non-head load with `possibleLoadViolation()`, for internal L1 evictions too and with `needsTSO` either 0 or 1. The `ReExec` traps at the head and squashes the younger, already-exposed loads. The exposing load's own fill can be the eviction that triggers this in a 2-way set.
- **Contradicts:** §IV-A1 p4: a USL becomes safe only when it is "preceded in the ROB only by instructions that cannot be squashed by any of the squashing events in Table I", and Table I p3 lists "address alias between two loads". Also §V-D p6: "no squashed transaction can change the state of the caches".
- **Caveat:** single-core, the squashed correct-path load re-executes with the same address, so a relational checker (AMuLeT) sees nothing. This fits AMuLeT's clean Patched campaigns (Table 6). A value-dependent leak needs the re-executed value to differ (a cross-core write).
- **Evidence from existing traces (read-only scan, no runs):** in all 3020 pipeviews of `/tests/simspect_fixed_20261030/results/STT_6_invisispec_v2hooks_futuristic__20261107`, there are 19,594 `L1D:expose`/`validate` and `SB:buf_release why=expose|validate` events and **0** cases of an exposed seq followed by an older `ROB:squash`. So STT_6 does not reach it. The scan script was kept only in the scratchpad; rewrite it if needed.
- **SimSpect:** the Futuristic criterion sets vp(i) = the first expose/validate, so a premature expose makes itself legal and `check_footprint` misses it (Question 2). The "exposed, then squashed" signature is cheap to check on any trace.
- **gem5 check (2026-11-09, bug-investigate-is2): real (the mechanism fires in gem5), but not reached by our pipeline.** Scratch: cafe2 `/tests/simspect_alloy_20261108/bugwork/is2/` (`is2scan.py`, `is2scan.json`, `scan.log`; hand test in `hand/` (`gen5.py`, `run5.sh`, `win.py`, trace `hand/v5_f160_y2/m5out/pipeview.txt`); nothing running).
  - **Generated tests: 0 / 600.** `is2scan.py` re-ran 300 `E12a_STT_6_fv2` ld tests per branch mode (seeded shuffle 1109 of each `code_20261109/results/E12a_STT_6_fv2__latest/<mode>/ld/window-results.json`), with the campaign config verbatim including per-branch stalls (`spt_taint_probe.probe_one`, grid 0) and only `Commit,LSQUnit` added to the debug flags. Results: 0 errors, 0 `Conflicting load` (the ReExec setter, `lsq_unit_impl.hh:651`), 0 faults or traps, and **0 "exposed then squashed"**. That signature is decided from one trace: some seq S has an `L1D:expose`/`L1D:validate` event at t1, followed by a `ROB:squash` at t2 ≥ t1 with squash seq < S. The 600 traces contain 2,116 expose/validate events. Possible-violation marks are in 600/600 and store-load order squashes in 5. The campaign's `_sweep_raw/*.json` rows do not keep the event list, so the reruns were needed. This agrees with the old corpus: 0 in 3020 Futuristic traces (above) and 0 `Conflicting load` in IS-1's 6047 + 300 traces.
  - **Why our tests never get there.** Three conditions have to line up, and the last one is the hard one. (a) P2 is marked `possibleLoadViolation` (common). (b) P2 is exposed or validated, which needs every older instruction complete and safe. (c) While P2 still is **not the LQ head**, an L1 eviction of P2's line hits it: `checkSnoop` skips the head (`lsq_unit_impl.hh:590-608`), and for an internal eviction only `possibleLoadViolation` loads get `ReExec` (`:643-660`). But once everything older is safe, commit drains it at 8 per cycle, and IEW frees LQ entries one cycle later (`commitLoads`, `:1005-1011`). So the eviction has to land within roughly (instructions between P2 and the nearest older uncommitted load) / 8 cycles after P2's expose. Speculative misses in this build pick a victim right away (the UV1 path, `L1D:evict ... req=specld`), but they leave no line behind (`SPEC_LD` → `IX`). Validate and expose fills come only after the load's own data returns, which in the hand-test traces took 15 or more cycles (hand variant v3: the first Y load's validate fill at 795500, but P2 had already left the LQ at 785000).
  - **Hand test (mechanism check only; per Anna's rule it does not count as found by us).** `hand/gen5.py 160 2` is a standalone 2-iteration loop on the E12a gem5 flags. Iteration 1 warms the I-cache, and each iteration re-primes L1D set 0 with L=`buf+0` and X=`buf+2048`. The body is: C, a cold load that makes P0's address late; P0 = `mov rbx,[r8+rax]` (line L); 160 nops; Lf = `mov r9,[r8+64]` (stays at the LQ head while commit drains the nops); P2 = `mov rcx,[r8]` (line L, executes before P0); W = `mov r11,[r8+2048]` (line X, younger; its expose makes X the MRU way); 2 imuls on rbx; then Y1 = `[r8+rdx+512]` and Y2 = `[r8+rdx+1024]` (set 0). Trace (`hand/v5_f160_y2/m5out/pipeview.txt`): P0 executes and marks P2 (`Found possible load violation`), then `724500 L1D:expose seq=817` (P2, expose-only, so safe as soon as it is sent, `base_dyn_inst.hh:807-818`); `725000 L1D:expose seq=818` (W); `728500 L1D:evict seq=826 ... victim=0x1000 req=specld` (Y1's speculative miss evicts L); `728500 Conflicting load at addr 0x1000 [sn:817]`; `734500 Committing instruction with fault [sn:817]` / `Generating trap event`; `741500 ROB:squash seq=816` / `Squashing from trap`. So two loads that had already been exposed (817, 818) are squashed after they touched the L1. The single-trace signature fires on exactly those two seqs. It does not fire on variants where the eviction comes before P2's expose: in v4 y0, P2 gets `ReExec` in the same tick it becomes safe, and the trap is still taken.
  - **Caveats.** In this demo the eviction comes from Y1's speculative miss replacement, i.e. the already-reported UV1 defect. The other route, an exposed or validated load's own fill, was always too slow in the variants tried, because the window is about 20 cycles with a 192-entry ROB. Both exposes were L1 hits, so the squashed exposes changed only replacement state, plus Y1's eviction. Single-core, the re-executed load reads the same value (caveat above).
  - **Stage-2 shape that would reach it:** (i) a same-line load pair whose older load gets its address late (from a cold load) while the younger one executes first; (ii) an older load, followed by ≥ ~100 ROB-filling instructions without destination registers, right before the younger load (with `add`s, rename stalls on physical registers in the v3 variants, and P2 never ran early); (iii) a younger exposed load to a second line of the same set, so that the alias line becomes LRU; (iv) a load to a third line of that set (512 B stride on the 1 kB/2-way L1D) whose address depends on the older load's value through 1–3 cycles of ALU work, so that its miss lands after the exposes but before the LQ drains. Our stack-slot concretization never produces (ii)–(iv). Detection would also need the "exposed then squashed" term (Question 2).

## IS-3. Cross-core: a Spec-GetS turns another core's Exclusive grant into Shared

- **Code:** `mem/protocol/MESI_Two_Level-L2cache.sm:1095-1098`, `transition({IS, ISS, IEE}, L1_GETSPEC, IS)`. Without the Spec-GetS, `ISS`/`IEE` would reach `MT_MB` and send `DATA_EXCLUSIVE` (`:1041-1055`, actions `:646-675`, which assert that there are no GetSPEC requesters). In `IS` the line reaches `SS` and the GETS/Expose requester gets plain `DATA` (`:1057-1065`), so its L1 ends in S instead of E (`L1cache.sm` `IS, Data_all_Acks, S`).
- **Contradicts:** §VI-E1 p9: a Spec-GetS works "without changing any cache or coherence states". §III-B p3 protects the E/S state of any level of a multiprocessor hierarchy.
- **SimSpect:** not reachable single-core: the per-core Sequencer refuses a second read to a line already outstanding (`Sequencer.cc:240-268`, `Aliased`). Out of reach of our runs; it is listed in `invisispec.json` `not_covered` (remote-core coherence).
- **2-core feasibility check (2026-11-09, bug-investigate-is3): feasible, gem5 runs it, but not this round (est. 3-5 working days + an Anna decision).** Scratch: cafe2 `/tests/simspect_alloy_20261108/bugwork/is3/` (`run2core.py`, `run_n1/`, `run_n2/`, gzipped traces; 11 MB; nothing running; no `/tmp` dirs: outputs and TMPDIR inside bugwork).
  - **What runs today, with no gem5 or harness edit.** `se.py` already supports it: `--num-cpus=2` builds two O3 CPUs and Ruby makes one L1 controller per CPU with the shared L2 (`se.py:216-218`, `:300-301` asserts `num_cpus == len(ruby._cpu_ports)`). With one `--cmd`, every CPU gets the same Process (`se.py:276-277`), so CPU1 stays idle until the program calls `clone`; this build implements it (`src/arch/x86/linux/process.cc:279`, `cloneFunc` in `syscall_emul.hh:1242`), and `exit` only ends the simulation on the last running context (`syscall_emul.cc:101-106`). Two `--cmd`s (`;`) would give two processes with separate address spaces, so they could not share a line; the second thread has to be a `clone`d thread.
  - **Experiment.** `run2core.py` imports the code_20261109 `gem5_common` unchanged, calls `run_gem5` with the E12a flags (`E12a_STT_6_fv2.jsonc` extra_args, branch annotations, resolve stall 5000) plus `--num-cpus=2`, and replaces only the entry stub: `call is3_setup` clones a thread (flags `0x50f00`, own 16 kB stack in .bss) that loads the test's `-8(%rsp)` line 20,000 times, then the test runs and exits with `exit_group`. The test function stays at `0x401020` (entry grows 17 → 22 bytes, still under the 16-byte-aligned slot). Stem `inst-002372` (STT_6_fv2, mispredict_not_taken). Result: both runs exit normally; 1-CPU 285 insts, 0.10 s host, 3.4 MB trace; 2-CPU cpu0 297 insts and cpu1 60,005, 7.3 s host, 181 MB trace. Cross-core sharing is real: the reader's GETS takes the test's M line (`L1D:coh ... pc=0x401cd4 ... ev=Fwd_GETS:st=M:nst=S`, tick 251000), and the test's later spec loads of that line go to the L2 in `SS` (`L2:hit ... ev=L1_GETSPEC:st=SS:nst=SS`, ticks 3276000/5768000).
  - **Observability.** The hook lines already log every Ruby transition with `ev=/st=/nst=`, so the IS-3 event is a single-trace signature: an `L2` line with `ev=L1_GETSPEC:st=ISS|IEE:nst=IS` (`L2cache.sm:1095`), followed by the other core's L1 fill `Data_all_Acks:st=IS:nst=S` where it would have got E. No differential run is needed.
  - **What would have to change (cost).** (1) Harness, ~1 day: the entry stub and reader object in `build_binary` (`gem5_common.py:114-147`); `_COMMIT_SQUASH_RE` only matches `system\.cpu\.commit` (`gem5_common.py:762-763`), and with 2 CPUs the names are `system.cpu0`/`system.cpu1`, so check_br's squash ticks would silently vanish; `parse_pipeview_by_seq` keys on seq, and O3PipeView and `O3PipeView:simspect:` lines carry no CPU id, so the two cores' seqs collide (the PC range of the reader code is the only separator). (2) Hooks, ~0.5-1 day + an InvisiSpec rebuild: add a requester/CPU id to the simspect lines. Without it, L2/DIR events are attributed through a per-line most-recent-cause seq (`invisispec.json` `not_covered`, 'L2/DIR/LLCSB attribution'), which mixes the two cores. This is a gem5-hooks edit and needs approval. (3) Criterion, ~0.5 day: a new `check_footprint.py` term for coherence-state changes caused by an actor's GETSPEC; today the checker only counts installs/evictions per structure. (4) The reader, 1-2 days and the real risk: IS-3 needs the GETSPEC to arrive while the L2 is fetching the line from memory for the reader (`ISS`/`IEE` exist only from `NP`, `L2cache.sm:987`, `:998`), a window of one memory latency. A simple spinning reader hits its own L1 after the first fill, so it gives that window once. To repeat it, the reader would have to evict the line from the 2 MB/16-way L2, which takes 17 lines 128 kB apart, and inclusion would also invalidate the test core's copy. And it must target the transmitter's line, which is known statically only for stack addresses. (5) Cost per test: about 70x host time and 50x trace with a 20k-iteration reader. A shorter reader, or `--debug-ignore` for cpu1 (untested), would cut that.
  - **Side effects to know about.** Adding the reader's .bss moved the test's physical lines (the stack line is `0x3dc0` in the 1-CPU run and `0x7dc0` in the 2-CPU run), and the reader puts the test's lines into S. So a 2-core run changes the test's own cache behaviour. Its results are not comparable with the single-core campaigns.
  - **Verdict:** feasible with ~3-5 days (harness + hook id + criterion + reader design), not this round. It is also gated on a scope decision (URGENT_TODO DECIDE 'IS-3 2-core'). Found by us: no (no generated test runs on 2 cores).

## Reportability: what generation would produce IS-1 / IS-2

Per Anna's rule we report only what the pipeline finds, so IS-1 and IS-2 stay "source findings, not yet reportable" until generated tests hit them. No hand-written gadgets and no differential testing.

**What both shapes need, besides the STT_6 core that the pipeline already makes** (a mispredicted, held branch with a wrong-path transmitter load):

- (i) **A load-load alias that executes out of order.** Two loads to one line, where the older one's address resolves later than the younger one's, so `checkViolations` marks the younger one `possibleLoadViolation` (`lsq_unit_impl.hh:836`).
  - Same-address pairs already occur often in our concretization, because loaded values are 0 and probe-addressed accesses share `probe_mem+0` (`VOCAB_TABLES.md` store-separation note).
  - What is missing is the ordering: the older load's address path has to be longer.
- (ii) **An L1D eviction of that line while both loads are still in the ROB.** With the E12 L1D (1kB/2-way = 8 sets, 512 B set stride), that takes accesses to 2 more distinct lines in the same set.
  - Today's tests touch only a few lines, mostly in different sets, so this almost never happens.
- (iii) **IS-1 only: timing.** The mispredicted branch must resolve inside the ~13-cycle trap window of the re-executed load (`trapLatency`, `O3CPU.py:113`).
  - IS-2 needs no branch timing. The exposing load's own fill can be the eviction.

**Routes, all opt-in, from cheapest to most work:**

1. **Fanout v2 with longer address paths (exists, FV-1/FV-2).** Value-preserving splices (`imul1`, `lea0`, `rol_ror`, …, `specs/fanout/stt.json`) on the rf edge into an *older* load's address lengthen its path, which gives (i) without changing any value.
   - It does not give (ii): the template's fillers are ALU-only (`add`, `xor`, `and`, `imul`, `lea`, `shl`).
   - No fanout template exists for the InvisiSpec footprint units yet.
2. **New vocab: read-only load fillers ("FV-mem").** Fillers that load from a probe-array address and write only unused registers, placed in the committed pre-window region. Two address families, both drawn at random:
   - (a) the same line as an Alloy load's address, to make alias pairs;
   - (b) `probe + k × (L1D sets × 64)`, to make set conflicts.

   The stride must be derived from the run config's L1D geometry (`--l1d_size/--l1d_assoc`) and not hard-coded, so the rule stays general and isn't tuned to this bug. With route 1 this covers (i) and (ii) for both shapes.
   - Safety: read-only loads in the committed region do not change any Alloy rf edge. They do change cache state, which is the point, and per the model audit's insertion rules they are allowed for STT-family and footprint units (rules 4 and 11 in `MODEL_AUDIT_SPT_RECON.md`; keep them off for SPT, rule 9). This is a vocab/Stage-2 change and needs Anna's sign-off, like FV-1.
3. **IS-1 timing knob (exists).** Sweep the held branch's stall densely (`sweep.unresolved_points`, e.g. 0..60 step 1) instead of E12's fixed long hold, so that some tests resolve the branch inside the trap window. This needs no code, only a config.
   - Under today's window, these tests would be scored only up to the resolve. That is why Question 1 has to be decided first.
4. **IS-2 detection.** Even with routes 1 and 2, the Futuristic actor's vp (= first expose/validate) scores IS-2 as legal. It needs the "exposed then squashed" term (Question 2).
   - In single-core runs IS-2 re-executes the squashed load with the same address, so it would be reported as a mechanism violation, not an information leak.

1. **Spectre window vs IS-1 (updated in the resume pass).**

   **Options:**
   - (a) Keep the window ending at `resolve_visible`. IS-1 stays invisible.
   - (b) End the **shared** window at the squash that kills the branch's wrong path.

(c) is only worth it if we want to keep old numbers comparable.

   **Definition.** For each annotated unresolved branch b, the window ends at the first squash after b's resolve whose seq is ≤ b's seq. That is either b's own mispredict squash, or an older squash: a trap (IS-1), a memory-order squash, or an older branch.

   **Sources already in every trace:**
   - b's own squash: the Commit-debug line `Squashing due to branch mispred PC:` (`gem5_common.parse_commit_squashes`, `gem5_common.py:761-776`, already used by `check_br`).
   - Trap squashes: the Commit line `Squashing from trap` (`commit_impl.hh:616`). A trap squash kills the whole ROB, so it ends the window for every branch in flight.
   - On the AMuLeT builds, the `ROB:squash` hook line also carries the squashing seq.
   - A branch never squashed by the end of the simulation keeps ∞, as today.

   **What changes for the defenses that share the window.** The window is `gem5_common.check_branch_resolutions`, used by `check_ld`, `check_br`, `check_other`, `check_footprint` and the `check_ld_*` variants:
   - *Normal mispredicts: nothing changes.* Commit takes the IEW squash in the same tick that `markCompletedInsts` sets the branch ready (`commit_impl.hh:711-713`), so resolve_visible equals the commit squash tick. The release→visible gap is 1 cycle (`RESOLUTION_HOOKS.md`), and the squash arrives in that same commit tick.
   - *The window grows only where the squash is late*, which are exactly the cases Anna already classed as implementation bugs:
     - STT/ReCon pending squash: the A4 family, STT S4 (`SOURCE_AUDIT_STT.md`), and the STT upstream pending-squash fix noted in claudelog 2026-11-08 20:30;
     - the stock O3 `TrapPending` drop, which every O3 build shares (IS-1 here; also possible on STT, SPT and ReCon, not checked);
     - any squash that is broadcast late.
   - *Effect on hits:* it can only add hits, never remove them. All the added hits fall in a resolve-to-squash gap, so they are real wrong-path behaviour and not artifacts.
   - *Re-scoring:* traces have to be re-scored. Campaigns that kept every pipeview (the InvisiSpec/CleanupSpec/SpecLFB v2hooks runs) can be re-scored offline. The taint-defense campaigns kept pipeviews only for hits, so a non-hit that would become a hit needs a rerun.
   - *Prerequisite:* `check_footprint`'s actor `squashed_after_lc` already keys on squashed. It only needs the window bound changed.
