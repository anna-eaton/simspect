# gem5 hook audit: every SimSpect modification, every build (2026-11-07)

Read-only audit of every SimSpect change inside the gem5 trees on cafe2 (`gem5_dev` container, `/work/*`), held against Anna's rule: gem5 changes may only (R) read out state, (S) give speculation directives confined to the predictor, or (T) stall things we are allowed to stall without changing the defense's own decisions. Anything else is (V). No gem5 tree was edited, rebuilt or run. No git writes. Per Anna's 2026-11-07 change of scope, the three AMuLeT footprint builds (InvisiSpec, CleanupSpec, SpecLFB) are **not audited here** ("audit paused, Anna reviewing"). They appear only in the build list, with flags taken from the run configs.

Every diff referenced below is saved in [`hook_diffs/`](hook_diffs/) (full current diffs, not the 2026-10-20 captures in `gem5-hooks/`, which predate the 2026-10-30 resolve hooks).

## TL;DR verdict per build

The C++ hooks in every audited build are R, S or T. The real problems are (1) one non-hook source fix in amulet-STT, (2) config glue in `se.py` that sets defense parameters differently from the authors' own run scripts, (3) the slow-comm / `se_exp.py` configs that change O3 latencies globally (the paper's STT/SPT race leaks come from these), and (4) gem5-recon-stl being a stale copy without the 2026-10-30 resolve hooks.

**What `--scheme N` means depends on the build.** Kaxiras-group gem5 (gem5-recon*): enum `{Unsafe, Delay, STT, DoM}` (`src/cpu/o3/cpu.hh:455-461`), help text "0 Unsafe, 1 = Delay, 2 = STT" (`src/cpu/o3/BaseO3CPU.py:177-178`), injected into every `O3CPU` at `configs/common/Simulation.py:466-475`. Scheme 1 is what Pavlos's email (`documentation/docs/Files/email.txt:18`) calls NDA. In the code it lets a speculative load reach the cache and then withholds the load's writeback in the delay unit until the load is no longer speculative (`lsq_unit.cc:194-211` in `completeDataAccess`, released at `secure_scheme/delay_unit.cc:194-206`). So the email's label fits the code, and our docs' "1=Delay (eager delay-on-use)" (`specs/defense_units.json` unit 11) describes it wrongly. On `/work/stt`, `--scheme` is **our** glue (`configs/example/se.py:329-336`): 0 and 1 = UnsafeBaseline, 2 = STT + Spectre + implicit channel, 3 = STT off with threat model Spectre, which is the InvisiSpec-codebase "fence" (`src/cpu/o3/cpu.cc:430-433`), not DoM. On gem5-spt, `--scheme=2` becomes `SpectreSafeFence` (`configs/example/se.py:331-337`).

## How the audit was done

- **Baselines.** Git trees (stt, stt-dbg, gem5-spt): `git diff` against HEAD (cwfletcher/stt `e3283b9`, FPSG-UIUC/SPT `0d2be0f`), plus the untracked `se_exp.py` / `se_slowcomm.py` diffed against `se.py`. gem5-recon-modded: `diff -ruN` against `/work/gem5-recon` (the base per the owner). gem5-recon itself (no git, no pristine copy on cafe2): files with mtime after its 2025 base were found with `find -newermt` and diffed against upstream gem5 v22.0.0.2 (fetched read-only from GitHub; gem5-recon reports `gem5Version = "22.0.0.2"`, `src/base/version.cc:35`) to isolate the local edits from ReCon's own code. gem5-recon-stl: against its `*.pre-stl` backups and against recon-modded. amulet-STT: against the pristine `/work/STT_AE-v1.1.tar.gz`.
- **Binaries.** mtime against the newest source file, the rebuild logs (`/work/simspect_backups/resolve-hooks-20261030/<build>.log`: both 2026-10-30 rebuilds `rc=0` for all five resolve-hooked trees; `/work/gem5-recon-stl/stl_build3.log` `EXIT=0`), and hook format strings in each binary. For the recon family, I hashed the address-normalized disassembly of every `o3::`, `branch_prediction::`, cache and `StoreSet` function in five binaries ([`hook_diffs/binary_function_compare_recon_family.txt`](hook_diffs/binary_function_compare_recon_family.txt), tools in `hook_diffs/tools/`). Between the unhooked control and recon-modded, every function of ShadowTracker (28), DelayUnit (31), TaintTracker (25), ROB (34), Rename (68), Decode (43), InstructionQueue (76), BaseCache (120), Cache (160), StoreSet (22) and DynInst (58) is identical. The functions that differ are the ones the source diff touches (BPredUnit, Commit, IEW, CPU constructor, `LSQUnit::read`, `Fetch::fetch`), plus inlining and register-allocation noise in the same translation units (checked by hand for `LSQUnit::insertStore`, `commitLoad` and `IEW::writebackInsts`: differences only in inlined `RefCountingPtr::set` / `cprintf` code).
- **Defense signals.** For every T hook, I traced which signal the defense keys "resolved" on, to check that the stall holds that signal.
- **Not done.** No gem5 runs (not needed to confirm a panic). The earlier print-only proof for the resolve-hook rebuild still stands: 546/546 audit traces identical pre/post (`wiki/design/RESOLUTION_HOOKS.md` §1, §4).

## Shared hunk families (identical text in stt, stt-dbg, gem5-spt, amulet-STT; equivalent code in recon-modded)

- **H1. Branch-annotation plumbing: S (wiring).** `BranchPredictor.py` VectorParams `annotationBranchPCs` / `annotationForcedTargets` / `annotationResolveStallCycles`; `Options.py` `--branch-ann-file` / `--branch-ann-base`; `se.py` `load_branch_annotations` (stt `se.py:67-111` and `:288-293`; spt `:56-89` and `:287-292`; amulet-STT `:68-98` and `:290-295`; recon-modded `:88-148` and `:340-354`). Python only. It puts annotation values into predictor params, and not-taken modes get target 0 (no force). The harness's `mode: "simspect_force"` passes the derived target through. No simulator state is touched beyond the predictor's own params.
- **H2. Forced prediction in `BPredUnit::predict`: S.** stt/stt-dbg/spt `src/cpu/pred/bpred_unit.cc:324-346`, amulet-STT `:325-347`, recon-modded `:326-357`; constructor fills the maps (stt `bpred_unit.cc:80-88`, recon-modded `:76-118`); `bpred_unit.hh` adds two `unordered_map`s and a const accessor. After the normal BTB / direction / RAS lookup, an annotated PC gets `pred_taken` and target replaced: target 1 = not-taken fall-through (`advancePC`), anything else = taken to that address. Only predictor outputs (`pred_taken`, the next PC handed to fetch) and predictor-internal records (`predict_record.predTaken`, `.target`) change. The direction predictor's speculative history keeps the original guess and is corrected by the normal `squash` / `update` path: still inside the predictor. Limits, not violations: RAS push/pop has already happened before the override, so forcing a call/return would leave the RAS inconsistent (the harness only annotates Alloy jcc's); every dynamic instance of the PC is forced. recon-modded adds `PCStateBase::setInstAddr` (virtual; arm/generic/x86 `pcstate.hh` overrides call the existing `set()`) only to implement the taken override: S support, no other caller.
- **H3. Resolve stall in `IEW::executeInsts`: T.** stt/stt-dbg `src/cpu/o3/iew_impl.hh:1335-1386`, spt `:1377-1428`, amulet-STT `:1335-1385`, recon-modded `src/cpu/o3/iew.cc:1302-1395`. For a control instruction whose PC has a stall, `setExecuted()`, `instToCommit()` and the mispredict squash are deferred by N cycles in an `EventFunctionWrapper`; on release it checks `isSquashed()` (drop), then calls `wakeCPU(); setExecuted(); instToCommit(); activityThisCycle();` and `squashDueToBranch` if mispredicted. Why this holds exactly the defense's "resolved" signal and nothing else:
  - STT: `prevBrsResolved` needs `readyToCommit()` of every older control inst (`/work/stt/src/cpu/o3/rob_impl.hh:489-494`), and `setCanCommit` only happens in commit's `markCompletedInsts` after the release. STT's implicit-channel "pending squash" is applied in commit when it consumes the IEW squash (`commit_impl.hh:934-962`), so the released squash still goes through it.
  - SPT: same `readyToCommit()` rule (`/work/gem5-spt/src/cpu/o3/rob_impl.hh:534-537`); configImpFlow Lazy/Eager pending squash in commit (`commit_impl.hh:917-962`). No taint logic sits on SPT's IEW post-execute path for branches (only `wakeUntaintInsts` at `iew_impl.hh:1618`, outside the branch path).
  - Recon: `branchResolved(true)` is set in `markCompletedInsts` (`commit.cc:1489-1490`) after the release, and the ShadowTracker frees the shadow from it. A tainted branch is held at IQ insertion (`inst_queue.cc:1451-1457`), i.e. before it can execute, so the hook never bypasses it.
  - Same-cycle squash ordering: the release runs at priority `Default_Pri` = 0, before the CPU tick (`CPU_Tick_Pri` = 50; `src/sim/eventq.hh:149,162`), so IEW's tick then resets `fetchRedirect` (`iew_impl.hh:1189-1192`). That does **not** let a younger squash overwrite the released one: `squashDueToBranch` and `squashDueToMemOrder` keep the older seqNum themselves (stt `iew_impl.hh:487-488,520-521`; recon-modded `iew.cc:460-461,488-489`). Agrees with `wiki/findings/audits/2026-10-30/RESOLVE_HOOKS_CODE_AUDIT.md:79`.
  - Wake fix (edit 4): `wakeCPU()` is a no-op while the CPU is running. When the CPU slept because the ROB filled, it wakes it the way a late memory response does (524/536 traces unchanged; the 12 that changed were the frozen ones). It counts as part of the allowed stall: without it the stalled branch was never released.
  - Nuances, both minor and only affecting the held branch's own timing or predictor state: (a) `instToCommit` at release uses `wbCycle` / `wbNumInst` left over from the previous cycle, so after a cycle that overflowed writeback width the release can land 1 slot later (`RESOLVE_HOOKS_CODE_AUDIT.md:80`). (b) Because `fetchRedirect` is reset after the release, a younger memory-order violation detected in the same cycle still calls `instQueue.violation()` (store-set training) even though its squash is discarded by the seqNum guard. Predictor state only, and only in an exact-cycle coincidence.
  - `updateExeInstStats(inst)` is called at execute time (stats and the O3PipeView `complete` tick only).
- **H4.
