# Audit: the four `*_full` run configs (2026-10-28)

Scope: `results/STT_6_invisispec_full_spectre`, `STT_6_invisispec_full_futuristic`, `STT_6_speclfb_full`, `STT_6_cleanupspec_full` (run_config.jsonc + README.md). Audit only: nothing edited, no gem5 run, no git writes. Build sources read from cafe2 `/work/amulet/amulet-gem5-*_AE-v1.1/configs/{common/Options.py,common/Scheme.py,example/se.py,ruby/Ruby.py,ruby/MESI_Two_Level.py}`; old launchers read from cafe2 `/tests/simspect/results/` (they are not on the Mac). 12-minute budget, so items marked UNVERIFIED were not chased.

## Verdict

The configs are sound to launch with two caveats that matter. (1) `filter.xmit_kind: "ld"` is really ignored on the pipeline path, and `gem5.checker` overrides every kind, so these runs will put ALL STT_6 transmitters (ld + br_x + other_x, the full testset, not a 1500/mode sample) through `check_footprint.py`. The old campaigns ran ld-only samples. (2) The CleanupSpec "launcher's inject_stalls" claim is false: `run_cleanupspec_residue.sh` has no stall injection. It ran `check_ld_cleanupspec.py` directly on whatever `<stage-dir>` it was given, so whether the old residue run had the 5000-cycle resolve stall depends on that dir (UNVERIFIED). Every flag exists and parses with its value, and the `--scheme` last-wins override works for Futuristic.

## Sync

The local and cafe2 copies are byte-identical (md5 match on all 8 files).

## `--caches` + `--ruby`

There is no conflict. `gem5_common.py:run_gem5` always emits `--caches`. In both Ruby builds `se.py` (IS :299-341, CS :307-346) does `if options.ruby: Ruby.create_system(...)` and only the `else` branch calls `CacheConfig.config_cache`, so `--caches` is inert under `--ruby`. The only other use is the fastmem fatal (IS :263, CS :267), and that needs `--fastmem`, which no config passes. Dropping `--l2cache` for CleanupSpec is correct for the same reason: the grep found no `options.l2cache` in `MESI_Two_Level.py`.

## Hooks vs the old launchers

- **Resolve stall.** `pipeline._inject_stalls` (:397-426) sets mispredict branches to 5000, the xmit branch to 0, and correctly_not_taken to grid value 0 for `points:[0]`. That matches `inject_stalls` in `run_invisispec.py:35-49`, `run_invisispec_compound.py:31-42` and `run_speclfb.py:35-49`. `sweep.enabled:true` is required for this, as the comment says. **Exception:** `run_cleanupspec_residue.sh` has no inject step (see the verdict).
- **Test selection (unintended difference).** The old launchers staged ld-kind only, `--n 1500` per mode. The new configs run the whole testset and every kind, because `filter` is never read (no `filter`/`xmit_kind` filter in `pipeline.py` or `testrun.py`). This has three consequences. br_x/other_x transmitters will be judged by a footprint criterion, and whether `check_footprint` gives non-ld transmitters a meaningful verdict is UNVERIFIED. Results are not directly comparable to the old campaigns' counts. Runtime is much larger.
- **InvisiSpec.** The comparison against `_compound` is mostly right. Its "differs only by explicit L1I/L2/TBE flags" overstates it: the TBEs equal the defaults (2), but `--l1i_assoc=4` (default 2) and `--l2_assoc=16` (default 8) are real geometry changes, not restated defaults. The plain `STT_6_invisispec` campaign ran classic caches (no `--ruby`) with flags O3PipeView,LSQUnit only, which is the documented and intended difference.
- **SpecLFB.** The old run had no extra args: L1D 64kB/2, L1I 32kB/2, no L2. The new run uses L1D 1kB/2, L1I 32kB/8, `--l2cache` L2 2MB/16. These are intended and documented. The L1D shrink is flagged in the config as UNTESTED on this classic build.
- **CleanupSpec.** Same flags as the `.sh` minus the inert `--l2cache`, plus `--l1i_assoc=4`, `--l2_assoc=16` (defaults 2/8) and explicit TBEs=2. `--abs-max-tick=3000000000` replaces `SIMSPECT_GEM5_MAX_TICK`. `jobs` 4 is the same. The stall-injection difference is noted above.

## Comparison with AMuLeT's flags (2026-11-08)

**Question (Anna):** are the four AMuLeT-tree builds run with the same flags as in AMuLeT? **Answer: no, for all four.** In every hooks-v2 run the defense is switched on and the memory system matches AMuLeT's (Ruby for InvisiSpec and CleanupSpec, classic with an L2 for SpecLFB); `config.ini` confirms both. Each build still differs from AMuLeT in cache geometry, Ruby TBE count and system clock. InvisiSpec also differs in `needsTSO` and `allowSpecBuffHit`, SpecLFB in its branch predictor, and the InvisiSpec Spectre run in threat model. amulet-STT differs in everything that matters: classic caches instead of Ruby, Spectre instead of Futuristic, `needsTSO` 0 instead of 1, no L2. Our harness cannot reach AMuLeT's STT setting at all without a config-glue change. The CleanupSpec TBE=2 setting is the one real mistake that is costing results now: it is an inherited tree default, AMuLeT used 256, and it deadlocks 62% of tests.

**Scope and method.** Read-only, except for two tiny gem5 runs. Nothing in the repo, cafe2 configs, gem5 trees or `specs/` was edited, and nothing was written to git. AMuLeT side: cafe2 `/work/amulet-repo` @ `c871bdf`, which `src/benchmark_all.sh:21-61` builds into one YAML plus one flag set per defense. ### Real mistakes found

1. **CleanupSpec TBEs = 2 (accidental, now costing results).** `STT_6_cleanupspec_full/run_config.jsonc:39` copies the tree default. AMuLeT ran 256, and the CleanupSpec paper states 64 MSHRs (p11). With the 2kB/4 L1D it deadlocks 1861/3000 tests and hides 25 of the 40 hits that L1_TBEs=8 finds. Correction to the `full:36` comment: "assoc-2 deadlocks" is a TBE-exhaustion deadlock, made worse by small/low-assoc L1Ds; it is not an associativity property.
2. **amulet-STT cannot match AMuLeT's STT setting.** The harness always sends `--scheme=2`, which hard-codes Spectre in our glue and makes `se.py` skip `config_scheme`, so `--threat_model=Futuristic --needsTSO=1` in `extra_args` would be silently ignored. It also has no Ruby and no L2. No amulet-STT result can be presented as "AMuLeT's STT configuration".
3. **`--sys-clock` 1GHz everywhere (accidental omission).** AMuLeT uses 2GHz. config.ini shows it clocks the memory controller and the system port (and the classic membus on SpecLFB), so every build's miss latency differs from AMuLeT's.
4. **Our InvisiSpec `se.py` glue silently defaults `needsTSO` to 1** (`configs/example/se.py:350-351`), which is the opposite of the CPU default (False), of the authors' run script (0) and of AMuLeT (0). Every config passes `--needsTSO=1` explicitly anyway, so nothing ran differently, but a config that omits the flag would quietly get TSO.
5. **The configs mix reference points.** Each full config combines a SimSpect-amplified L1D, the defense authors' L1I/L2 associativity, and the tree-default TBE=2, which AMuLeT used only in its patched, amplified Table 6 (InvisiSpec). No published configuration matches any one of these as a whole. The README files document each choice, but none states this mix.
6. **Not a mistake:** no defense is inactive in the hooks-v2 runs (config.ini `simulateScheme` and the cleanup knobs match AMuLeT). The superseded `STT_6_invisispec` (classic caches, defense inactive) and `STT_6_speclfb` (no L2) were the "defense not fully enabled" cases, and the full configs already fixed them.

### Recommendations (each a recommendation with its tradeoff; not decided)

- **R1, CleanupSpec TBEs:** set them to 256 (AMuLeT) in any CleanupSpec run. Tradeoff: removes the defense-independent deadlock and the 62% test loss. It also removes MSHR contention, which CleanupSpec does not claim to protect anyway. L1_TBEs=8 is the measured minimum that completes 3000/3000; 256 is the parity value.
- **R2, `--sys-clock=2GHz` in every config:** no design content, closes an accidental gap. Tradeoff: it changes timing, so it requires reruns for comparability (cheap).
- **R3, an explicit AMuLeT-parity arm per defense,** using the "Matching flag sets" in HOOK_AUDIT, plus `--access-backing-store` for byte-level parity. Tradeoff: with cold full-size caches and no AMuLeT-style per-test L1D fill or flush, expect far fewer eviction and cleanup hits. That is the P-1 question below.
- **R4, keep the amplified geometry (1kB/2 or 2kB/4 L1D) as a separately labeled SimSpect arm and state it in the paper**, like AMuLeT's own §3.4 p7 / Table 6 amplification. Tradeoff: it finds more, but it is "smaller than anything AMuLeT or the authors ran", so reviewers may call those hits configuration-induced.
- **R5, pick one source for the non-amplified parameters per arm.** Parity arm: AMuLeT's L1I/L2 (IS 32kB/8, others 32kB/2; L2 2MB/8). "As published" arm: the authors' paper tables. Tradeoff: one more run per defense if both are wanted.
- **R6, InvisiSpec `needsTSO=0 --allowSpecBuffHit=0` in the parity arm.** Keep 1/1 only as a labeled "x86-TSO with SB reuse" arm if the paper makes a claim about it. Tradeoff: TSO=1 is arguably more faithful to x86, but neither AMuLeT nor the authors' own scripts ran it.
- **R7, SpecLFB `--bp-type=BiModeBP`** (both AMuLeT and the authors), after one smoke test that `BR:predict_force` still fires. Tradeoff: one smoke run; the gain is predictor parity.
- **R8, amulet-STT:** either drop it and cover STT with `/work/stt`, or make the two-line config-glue change so that `config_scheme` runs when `--threat_model` is given. Tradeoff: dropping it loses the AMuLeT-STT comparison point; the glue change edits a build config (needs your OK) and needs a `--ruby` smoke test.
- **State in the paper:** the harness-only additions (BTB force, 5000-cycle resolve stall, single-run footprint oracle in place of AMuLeT's relational 140-input oracle, cold per-test caches), plus every deliberate geometry or threat-model deviation that is kept.
