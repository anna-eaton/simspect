# Audit: does each campaign config actually activate its claimed defense? (2026-10-28)

Read-only audit (no edits, no runs, no git writes), done under an 11-minute cap, so some rows are marked UNVERIFIED. Trigger: today `STT_6_invisispec` turned out to have run without `--ruby` (InvisiSpec's cache logic was inactive) and `STT_6_speclfb` had no L2. Sources: every `results/*/run_config.jsonc` on cafe2 (`/tests/simspect`), the launchers `results/*/run_*.py|sh`, the local `runconfigs/*.jsonc`, and each build's `configs/example/se.py`, `configs/common/{Options,CpuConfig,Simulation}.py`, read over `ssh cafe2 docker exec gem5_dev`.

## Silent defaults that apply to every run

- `STAGE3_gem5/gem5_common.py:176-177` always adds `--caches` and `--scheme=<int>` (default 2). `:180-181` always adds `--abs-max-tick` (env `SIMSPECT_GEM5_MAX_TICK`, default 1e11). A later `--scheme=<Name>` in `extra_args` wins (optparse last-wins). This is used deliberately on SPT and InvisiSpec.
- **Without `--ruby`, every `X86_MESI_Two_Level` build still runs classic caches.** `--caches` reaches `CacheConfig.config_cache`, and the Ruby `.sm` defense logic is never built (amulet InvisiSpec `se.py`: the Ruby branch runs only `if options.ruby`, otherwise `CacheConfig.config_cache`). The binary's name says nothing about whether Ruby is active. This is the root of today's InvisiSpec bug.
- **SPT `--freeParam`:** `Options.py:352` defaults to 0, `CpuConfig.py:185` assigns `cpu.freeParam = options.freeParam` unconditionally, and `rob_impl.hh:764` sets `queueLimit = idealUntaint ? MAX : freeParam`. Any SPT run without `--freeParam=3` therefore has fwd/bwd untaint inert (VP-untaint only). This is already known (`claudelog.md` 2026-06-10 CONFIG BUG, `PAPER_PLAN.md:224`, D8).
- **Recon build:** `--scheme` (argparse int, `Options.py:413`) reaches the CPU only through `Simulation.py:466-469` (`if type(testsys.cpu[i]) == type(O3CPU()): ... scheme = options.scheme`). If that type test fails for `X86O3CPU`, the scheme silently stays at the `BaseO3CPU.py:177` default of 0 (Unsafe). I did not finish checking this; see the verification note at the end.
- **amulet STT build:** `se.py:297-300` sets `STT=True, threatModel=Spectre, implicitChannel=True` when `--scheme=2`. `config_scheme` is skipped (`:348`, `if options.scheme is None`). `:350-352` wires `fnc_commit_stall`. STT is active.
- **vanilla `/work/stt`:** `se.py:329-334` gives scheme 2 → `STT=True`, `threatModel=Spectre`, `implicitChannel=True`. STT is active.
- **gem5-spt:** `se.py:331-337` maps the string `"2"` to `SpectreSafeFence`. The trailing `--scheme=SpectreSafe*`/`Futuristic*` in `extra_args` wins.

## Recon scheme-injection check (open)

`Simulation.py:466` compares `type(cpu) == type(O3CPU())`. If the CPU is `X86O3CPU`, a subclass, the test fails and `scheme`, `sttBypass` and `allowLeaked` are never set, so every recon-build run would be Unsafe. To check without running anything: grep one existing recon campaign's gem5 stdout for `Injecting special parameters`.

Follow-up (finished after the time cap): `grep -rln "Injecting special parameters" /tests/simspect/results/Recon_6` returned nothing. A grep for `class X86O3CPU`, `class O3CPU` or `O3CPU =` in the recon build's `src/cpu/o3/*.py`, `CpuConfig.py` and `Simulation.py` also returned nothing. **This settles nothing.** The results dir may not keep gem5 stdout at all, and the class may be defined elsewhere. The next step is to find where gem5 stdout is kept for one recon run (or where `X86O3CPU` is defined) before reading anything into this.
