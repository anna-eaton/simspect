## AMuLeT code claims (`/work/amulet-repo/src`)

- **`executor.py:462` `include_replacements` is dead — VERIFIED.** Line 462 is `include_replacements = getattr(atk, "include_replacements", False)`. `atk` is used as a mapping two lines earlier (`if kywd not in atk`, `atk["sources"]`), so `getattr` on a dict key always returns the default `False`; the `replacements` branches inside `data_cache`/`instr_cache` can never run. Caveat: inferred from usage that `atk` is a plain dict (its constructor not read).
- **`executor.py:471-496` reads only L1 (plus TLB/BP/logs) — VERIFIED.** `get_raw_trace` handles exactly these sources: `data_cache` (`system.cpu.dcache` or `system.ruby.l1_cntrl0.L1Dcache`), `instr_cache` (`system.cpu.icache` or `L1Icache`), `dtlb` (`system.cpu.dtb`), `branch_pred_state`, `branch_predictions[_timing]`, `access_timing`/`access_order` (`accessLog`); anything else hits `Unsupported source` and exits. No L2, directory, or LLC source exists. `grep -i l2 executor.py` only finds command-line flags (`--l2cache` at :221, `--l2_size/assoc` :229-230, `--L2_TBEs` :217). The empty-TLB assert is skipped for SpecLFB (`if not CONF.SpecLFB`), as the table says.
- **`cleanupspec_analysis.py:90-100` diffs only L1I/L1D — VERIFIED.** `get_cache()` indexes `[system.ruby.l1_cntrl0.L1{which}cache]` and is called only with `'I'` and `'D'`; the I-only difference prints "UnXpec variant?".
- **(e) "AMuLeT never checks L2" — VERIFIED** for cache/coherence state (above). Minor caveat: the `access_timing`/`access_order` sources read a gem5 `accessLog` whose content (which levels it records) was not checked, so "never observes L2 timing" is not proven, only "never reads L2 state".

## Build claims (`/work/amulet/amulet-gem5-*_AE-v1.1`)

- **(a, part 1) InvisiSpec without `--ruby` builds classic caches — VERIFIED.** `IS/configs/example/se.py:336-341`: the non-Ruby `else:` branch does `system.membus = SystemXBar()` and `CacheConfig.config_cache(options, system)` (classic caches). `STAGE3_gem5/gem5_common.py:176` (the doc says :167; the `cmd` list starts at ~:168) appends `"--caches"` unconditionally and never `--ruby`, so `--ruby` can only come from `extra_args`. Note the se.py in this build carries a `SimSpect-compat` comment (the `--scheme=2` mapping is our patch, not upstream).
- **(a, part 2) the old `STT_6_invisispec` campaign ran without `--ruby` — VERIFIED.** The results dir is only on cafe2: `/tests/simspect/results/STT_6_invisispec/run_config.jsonc:22` binary `amulet-gem5-InvisiSpec_AE-v1.1/build/X86_MESI_Two_Level/gem5.opt`, `:33` `"extra_args": ["--scheme=SpectreSafeInvisibleSpec", "--needsTSO=1", "--allowSpecBuffHit=1"]`, no `--ruby`; `grep -- --ruby` over its `run_invisispec.py` launcher finds nothing. So the cache-side defense was inactive (classic caches); only the CPU-side scheme (e.g. the D-TLB miss fault) was live. No `config.ini` was found in the dir to confirm from gem5's own output.
- **(b) InvisiSpec `dir.sm:499-503` invalidates the M owner on a SpecFetch — VERIFIED (code), mechanism caveat.** `MESI_Two_Level-dir.sm:499` is `// [InvisiSpec] Is it secure?`, `:500-503` is `transition(M, {Fetch, Expose, SpecFetch}) { inv_sendCacheInvalidate; z_stallAndWaitRequest; }`; `inv_sendCacheInvalidate` (`:431-439`) sends `CoherenceResponseType:INV` to `getDirectoryEntry(address).Owner`. `I, SpecFetch → II` is at `:494-497`. So a SpecFetch to an M line gets exactly the same invalidate-the-owner treatment as a normal Fetch. Caveat: in MESI_Two_Level the dir's "owner" is an L2 bank, so this fires only when an L2 misses on a line the dir thinks an L2 owns (multi-bank L2 or an eviction race); with the single-core/single-L2 runs it is hard to reach, which the doc already says.
- **(c) CleanupSpec does not randomize the directory — VERIFIED.** `is_index_randomized` appears only in `src/mem/ruby/structures/CacheMemory.{hh,cc}`, `RubyCache.py` and `configs/ruby/MESI_Two_Level.py:78` (`is_index_randomized = options.rand_L2`, the L2 cache); `DirectoryMemory.*` has no randomization (grep `random` = 0 hits); `MESI_Two_Level-dir.sm` has 0 hits for random/unsquash/delay.
- **(c) no M/E→S delay — VERIFIED as absence-by-grep only (not proof).** grep for downgrade/unsquash/M-to-S/delay across `lsq_unit_impl.hh`, `lsq_unit.hh` and all `MESI_Two_Level-*.sm` finds only the stock `d2_sendDataToL2`/`d2ex_sendExposeDataToL2` "M downgrade" actions (`L1cache.sm:1164,1181`), which are the normal protocol responses, not a squash-safety delay. Single-core runs cannot trigger a remote-owner downgrade anyway.
- **CleanupSpec scheme table — VERIFIED.** `CS/configs/common/Scheme.py`: `Cleanup_FOR_L1` sets rand_L2, cleanupLQExecd/Inflight, l1d_mshr_tracking, random_repl_L1; `Cleanup_FOR_L1L2` adds `L2Inv` and `InternalInterferenceHit`.
- **(d) SpecLFB L2 protection only with `--l2cache` — VERIFIED.** `LFB/configs/common/CacheConfig.py:133-145`: `system.l2` is created only `if options.l2cache:`. `LFB/src/mem/cache/base.cc:804` is the commented-out `// && name() == "system.cpu.dcache"`, and `:806` `if(pkt->isRead() && !pkt->req->isHit_USL() && pkt->req->isUSL())` is in the shared `BaseCache`, so any classic level that exists takes the LFB path. Caveat: that the L2 actually sees `isUSL()` set relies on the request object being shared down the hierarchy (standard gem5, not traced here).

- **(d) old `STT_6_speclfb` had no L2 — VERIFIED.** `/tests/simspect/results/STT_6_speclfb/run_speclfb.py` (~:103) sets `SIMSPECT_GEM5_EXTRA = ""` with the comment "No extra_args", so no `--l2cache`.
