# Audit: SimSpect print hooks on the CleanupSpec build (2026-10-28)

Adversarial audit (read-only, 12-minute budget) of the CleanupSpec hooks described in `wiki/design/SIMSPECT_HOOKS.md` and diffed in `gem5-hooks/amulet-CleanupSpec/simspect_hooks.diff`, against the live tree on cafe2 `/work/amulet/amulet-gem5-CleanupSpec_AE-v1.1/src`. No code, config or gem5 file was changed; nothing was built or run. Line numbers: `L1` = `mem/protocol/MESI_Two_Level-L1cache.sm`, `L2` = `mem/protocol/MESI_Two_Level-L2cache.sm`, `diff` = the hooks diff, `RH` = `SimSpectRubyHooks.cc` inside the diff.

## Findings, ranked by severity

### 1. HIGH: `L2:cleanup_skip` for `SendAck_Cleanup_Invalidate` in NP is emitted on a recycle, so it can print repeatedly and does not mark a real ack

The L2 in-port triggers `SendAck_Cleanup_Invalidate` when the L2 entry is invalid (L2:430, comment "Proceed with ack"), but the active NP transition only recycles: `transition(NP, SendAck_Cleanup_Invalidate) { rrq_recycleL1RequestQueue; }` (L2:1147-1149); the ack-sending version `transitionA(NP, SendAck_Cleanup_Invalidate, C_NP)` is commented out (L2:1150-1151). A recycle is a valid transition, so `endTransition(valid=true)` runs every time the request comes back, and RH's rule `ev == "SendAck_Cleanup_Invalidate" && t.state == "NP"` emits `cleanup_skip` once per recycle (diff lines ~430-433 of RH). Consequences: (a) one cleanup request can produce many `L2:cleanup_skip` lines; (b) the print does not correspond to the L2 actually acking; the doc's mapping row "L2 `SendAck_Cleanup_Invalidate` (NP: line not in L2) → `L2:cleanup_skip`" describes intent, not what this .sm does. No verification run is reported to have printed an `L2:cleanup_skip`, so this path looks unexercised. Fix direction (needs Anna's OK, hook-only): emit only when the transition pops the request (not on recycle), or dedupe per (line, request).

### 2. MEDIUM: L2 cleanup decisions in transient states are unmapped (print nothing)

`transition(C_ISS, SendAck_Cleanup_Invalidate, CC_ISS)` (L2:1136-1139) and `transition(M_I, SendAck_Cleanup_Invalidate, C_M_I)` (L2:1162-1165) consume the cleanup request (pop) and move to CleanupSpec-only states, with no tag change, so no hook fires. The L2 settled that cleanup request there (ack without invalidating the line in this transition), and the trace says nothing. The doc's claim "complete for every cleanup-family event in ... L2cache.sm" is not true. The many stall/recycle transitions (L2:1110-1112, 1174-1178, 1187-1194) correctly print nothing.

### 3. MEDIUM: `DropIncomingPacket*` (the moment an in-flight load's fill is actually discarded) is not mapped and not mentioned in the doc

L1 declares `DropIncomingPacket`, `DropIncomingPacketnUnblockL2`, `DropIncomingPacketnUnblockRevertL2` (L1:157-159). They fire when a response arrives after an inflight cleanup (`tbe.Inflight_cleanup_recvd || L1Dcache.cleanup_inflight_received(addr)`, L1:484-497) or with no TBE (L1:472-482), and their transitions (L1:2874-2891) only send unblock/revert and pop the response: no tag change, so nothing prints. The hooks emit `cleanup_drop` only at the decision point (`Inflight_CLEANUP_reqs` in NP, L1:2818-2833), and the dropped data's arrival is invisible. Not wrong as a decision trace, but: (a) the doc's "complete for every cleanup-family event" omits these three events; (b) the same events also fire for non-cleanup reasons (TBE invalid), so they are not purely cleanup; (c) if a consumer needs "when did the speculative fill stop being able to land", there is no event. Also note `L2InvAckRecvd` (L1:509) is unmapped (fine: per-request ack bookkeeping).

### 4. MEDIUM: `cleanup_restore` is printed when the rollback is fired, not when the victim line is valid again

`transition({NP,I}, Load_ROLLBACK, IS)` (L1:2722-2729) does `oo_allocateL1DCacheBlock; i_allocateTBE; a_issueGETS; clf_...fired`. The hook prints `cleanup_restore` at the tag allocate (RH `onCacheAllocate`, `contains(t->event, "ROLLBACK")`), i.e. at the tick the GETS is issued. The line is in IS (Busy) until the data returns; the done marking is `dir_done_if_rollback` / `cld_...` later (L1:1790-1815). The data-return transition prints nothing (no second allocate). So the `cleanup_restore` tick is the restore's start; `cleanup_done` (LSQ) is the only completion marker. Any timing criterion that treats `cleanup_restore` as "victim back in cache" is early by one L2 round trip. Line attribution is right: `Load_ROLLBACK` is triggered on `install_lineaddr` (L1:797), so `line` = the victim being restored and `seq` = the cleanup request's (the squashed load's) seq.

### 5. MEDIUM: rollback-space replacement is printed as a plain `evict` (no `sq`), with `line` = the spec line

When the set is full, the dispatcher triggers `L1_Replacement` on `victim_addr = cacheProbe(install_lineaddr)` (L1:800-810) while processing the cleanup request for the spec line. RH `onCacheDeallocate` takes the `Replacement` branch: `incoming = g_msg.line` (the cleanup request's spec line, not `install_lineaddr`), reserves a fill id for that spec line (which never fills), and prints `evict ... sq=-`. So a cleanup-caused eviction of a possibly committed line is not tagged as cleanup activity, and its `line` names a line that was already cleanup-invalidated. The doc lists the line/cause mismatch as a gap; it does not say that `sq` is missing, so a per-squash count of cleanup side effects will miss it. The stale `g_pendingFill` reservation is harmless (`takeFill` requires a seq match, `sim/simspect_hooks.cc:140-150`).

### 6. LOW-MEDIUM: L2 cleanup events take `seq` from the per-line "most recent cause" map, so `sq` can be wrong

L2 `Cleanup_Invalidate(_clean)` → `cleanup_inv` (e.g. L2:1197-1201, 1226-1236) runs on a protocol message, so RH `attr()` uses `getLineAttr(g_msg.line)`, not the cleanup request. If a correct-path request to the same line started after the squash (and set the line's attribution when it allocated an L1 TBE), the L2 `cleanup_inv` gets that later seq, and `sqForInst(seq)` gives the wrong squash id or none. L1 decision events are exact (CPU `RubyRequest`, RH `noteRubyRequest`).

### 7. LOW: `g_msg` is never cleared after a peek ends

`noteMsg` sets the global `g_msg` after every peek (diff `PeekStatementAST.py`) and nothing resets it. A `CacheMemory` allocate/deallocate/setMRU or TBE alloc reached outside a peek (for example from a controller's wakeup without an in-port message, or from Sequencer code) would be attributed to whatever message was peeked last, possibly in another controller. Not observed; flagging as a latent attribution risk.

### 8. Not a hook artifact: UV4 "cleanup_skip on both lines"

The split-load print sits exactly at the native branch `if(loadQueue[load_idx]->isSplitReq()){ ++lsqSquashedLoadsSplitReq; //TODO: Cleanup For SplitReq ... setSquashBuffered(false); //Cleanup Done` (diff hunk `@@ -2441` in `lsq_unit_impl.hh`). CleanupSpec issues no cleanup request for a split load, so "skip on both lines, zero `cleanup_inv`" faithfully reports the native behavior (the UV4 hole), and the ref binary had identical ticks (1251500). One caveat not checked in time: whether this branch is reached for a split load that never issued; if so, `physEffAddrLow/High` could be unset and the skip lines would carry a bogus `line`.

### 9. Checked and correct

- L1 `Inv_CLEANUP`: `{S,X}` and `E` deallocate (`ff_deallocateL1CacheBlock`, L1:2685-2699) → `cleanup_inv`; `{NP,I}` (`clirs`, L1:2678-2681) and `M` (`clirs2`, L1:2701-2704) → `cleanup_skip`; transient states (all `AccessPermission:Busy`, incl. `IX` L1:86, `M_I` L1:90) recycle and print nothing. `M` getting `cleanup_skip` (no undo) is native CleanupSpec behavior, worth knowing.
- `Load_ROLLBACK` on `{S,E,M,X}` (L1:2735-2738) → `cleanup_skip`; on transient → nothing; `Skip_ROLLBACK` (L1:2742-2745) → `cleanup_skip`, triggered on the rollback target line (L1:792). These recycle the request but the dispatcher moves on to the next step once the step is marked done, so each prints once per request.
- `Inflight_CLEANUP_reqs`: NP → `cleanup_drop` (L1:2818); `{M_I,I}` → NP → `cleanup_skip` (L1:2853-2856). `Drop_Load_Cleanup_Inflight` → `cleanup_drop` (L1:2868). `Skip_Inflight_Cleanup` → `cleanup_skip` (L1:2861).
- Behavior/timing: every hook only reads simulator state (ROB `instList` scan, LSQ `physEffAddr*`, `RubyRequest` fields) and writes hook globals. The SLICC `beginTransition/endTransition` wrapper does not change the transition result. Consistent with the doc's identical-ticks verification.

### 10. Not verified (out of time)

- `cleanup_done` exactly once per squash: it is emitted at the single final `return true` of `LSQUnit::clearLoadQueue` (diff hunk `@@ -2760`, tree `cpu/o3/lsq_unit_impl.hh:2721`), but `clearLoadQueue` has three callers (`iew_impl.hh:773`, `lsq_impl.hh:177`, `lsq_unit_impl.hh:1944`). If it can return true through that path more than once per squash (for example on every call while no squash is in progress, or once from IEW and once from the LSQ in the same cycle), `cleanup_done` will print more than once. Overlapping squashes (a new squash before the previous cleanup finished) would print one `cleanup_done` with the latest `squashfrom_seqnum`, leaving the earlier `sq` without one. Check the guards at the top of `clearLoadQueue` and count `cleanup_done` vs `ROB:squash` in an existing verify log before relying on it. Partial check: `clearLoadQueue` returns false early when `!squashbuffer_used`, when `!squashbuffer_empty`, and while `skippedCleanupReqs + loadsInflightCleanupIssued + loadsExecutedCleanupIssued - cleanupAcksReceived > 0` (tree `lsq_unit_impl.hh:2730-2738`), so the print is at the true "all acks in" point and repeats are unlikely if `squashbuffer_used` is cleared on success (not confirmed). It also means a squash that buffered no loads gets no `cleanup_done`: consumers must not expect one `cleanup_done` per `ROB:squash`.
